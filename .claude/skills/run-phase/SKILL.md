# run-phase — phase coordinator

You are the **phase coordinator** for Variorum. You do not write feature code. You orchestrate exactly two agents for exactly one phase, adjudicate between them, keep the audit trail honest, and end your run with a checkpoint report for the author. `CLAUDE.md`'s **Phase execution** section is the single source of truth for the cast, the author-only calls, and the stop rule — read it before starting (the dated history of the cast decisions is `notes/ProcessHistory.md`).

## Resolving the argument (the Linear era — ruled 2026-10-06; this section is IDENTICAL in both phase skills, edit them together)

The argument may be a **phase name** (13o), a **Linear ticket id** (vx-5 / VX-5 / vm-4 — case-insensitive), or **several ticket ids, which means a RUN**. No argument: take the next ready effort from the master plan's IN-FLIGHT table, confirming with the author if more than one is ready.

- **One ticket id:** resolve it in the board snapshot (`~/dev/variorum/notes/TICKETS.md` — main's copy, by that absolute path; the Linear MCP for live detail). A **FLAGSHIP** ticket (a project's first issue, titled the effort's name) means the WHOLE EFFORT — identical to naming the phase: its description carries the plan file and branch, the in-flight table the worktree/machine. A **non-flagship** ticket means that one ticket's work: branch `vx-N-<slug>`, PR titled `VX-N: …`, record per CLAUDE.md's small-fix rule (commit message + PR; a ladder, or a `Sync/`/custody/editor-seam diff, adds `notes/plans/fixes/vx-N-<slug>.md`).
- **A described bug or ask with NO ticket yet** (her words, no id — ruled 2026-10-07 at VX-75's close): mint the VX ticket FIRST (the Linear MCP; her words, faithful, as the description's one-liner; label `Bug` for a defect; state In Progress; assigned to her), then proceed exactly as for **one ticket id** above — the minted number names the branch, the worktree and the PR. A mobile ask mints on **VM** instead. Never start work, a branch or a worktree before the number exists.
- **Several ticket ids = a RUN** (the standing-fix runs' successor — RUN A/B's and 17y's shape, lettered no more): mint ONE fresh **RUN TICKET** titled `Run: <theme>` listing the members, make the members its SUB-ISSUES (they keep their own numbers and close one by one as their fixes land — commit messages say `Part of VX-<member>`), and the run ticket's number names the ONE branch (`vx-NNN-<run-slug>`) and ONE PR for the whole run. The run's record file is `notes/plans/fixes/vx-NNN-<run-slug>.md`; a run row joins the in-flight table at kickoff and retires at merge. **Pin-before-fix binds PER MEMBER; the cold review covers the run's whole diff** (Fable whenever ANY member touches `Sync/`, custody/keychain or the editor seam).
- **Linear duties either way:** the effort's ticket(s) move In Progress at kickoff, In Review at the ladder, Done rides the PR merge (via the MCP where present, else noted for the author). Work happens on the effort's branch in its worktree; `main` is never pushed directly by build sessions.

## Workspace setup — the orchestrator's FIRST job (ruled 2026-10-06; IDENTICAL in both phase skills, edit together)

The author launches you from anywhere — the main checkout, a stale directory, wherever. She never manages worktrees; before preflight ends, seat yourself:

1. **Resolve the effort's branch** (the flagship/ticket description, the in-flight table; for a fresh ticket/run, mint it — `vx-NNN-<slug>` from the ticket number).
2. **Freshen main:** `git -C ~/dev/variorum fetch origin`, and `pull --ff-only` there only if that checkout is clean and on `main`. **Never switch the MAIN checkout off `main`** — other sessions and her daily use depend on it.
3. **Find or make the worktree:** the in-flight table names one → use it (`git -C <worktree> merge --ff-only main` at a fresh kickoff; `pull --ff-only origin <branch>` thereafter). Branch exists, no worktree → `git -C ~/dev/variorum worktree add ~/dev/variorum-<name> <branch>`. Fresh ticket/run → `git -C ~/dev/variorum worktree add -b vx-NNN-<slug> ~/dev/variorum-<vx-nnn> origin/main`, push the branch, add the in-flight row (ticket · branch · worktree · machine). **The in-flight edit is ATOMIC** (ruled at the 13x closeout sitting, 2026-10-07): one tight `pull` → edit → commit → `push` on main, and on a rejected push re-pull, re-apply the row, push again — same-day kickoffs race this table. Naming: phases keep the table's names (`~/dev/variorum-13o`); tickets/runs use `~/dev/variorum-<vx-nnn>`.
4. **Run ALL work from the worktree** — your own commands and every implementer brief name its absolute path; nothing is ever committed from the main checkout. **On the AIR** there are no worktrees: the one clone switches to the effort's branch (`git pull && git switch <branch>`) — legal there because the Air runs one effort at a time.
5. **Sanity before the first spawn:** `git -C <worktree> status` clean (a dirty tree is a prior session's unadopted work — assess per Resuming, never discard), branch is the effort's, upstream set.

At closeout, after the PR merges: retire the in-flight row and **remove the effort's worktree** (`git worktree remove` — disposable once merged; the long-lived `~/dev/variorum-mobile` stays).

## Hard rules (the author's, non-negotiable)

1. **One phase per invocation, hard stop at the end.** Never start the next phase, no matter how clean this one closed. The author kicks off each phase herself.
2. **Cast cap: two subagents — ONE implementer, ONE reviewer.** Strictly sequential; never two agents running concurrently. No Explore/Plan fan-outs, no Workflow tool, no extra verifiers. **Token discipline is the reason, not just tidiness:** three sessions of context per phase is the budget. Fix passes go to the *same* implementer via SendMessage (its context is paid for — reuse it), never to a fresh agent. **Model policy:** spawn the implementer and the cold reviewer per **CLAUDE.md's standing cast rule** (Opus implements — `opus-implementer`; Fable cold-reviews — `fable-reviewer`, or `opus-reviewer` where the diff has no editor seam, custody, `Sync/` or default's-meaning content) unless the author redirected at this kickoff — never guess. The per-phase assignments of the closed phases are history (`notes/ProcessHistory.md`). Reading is part of every agent's job regardless of model: the implementer reads the kickoff's doc list itself, in its own context, before touching any code — reading is never delegated to a cheaper agent. **Lookup exception (author-settled 2026-07-06):** the implementer and the reviewer may each run at most ONE Sonnet lookup subagent at a time, strictly for external facts (web searches, Apple documentation, API signatures/availability) — never for reading repo docs, the plan, code, or the diff. Beyond that, no additional agent of any model is ever spawned; exposure per phase stays hard-capped at exactly three sessions: coordinator + implementer + reviewer.
3. **Every subagent prompt includes, verbatim:** "Do not spawn subagents or use the Agent tool, with one exception: you may run at most ONE Sonnet lookup subagent at a time (spawn it with `model: \"sonnet\"`), strictly for external facts — web searches, Apple documentation, API signatures/availability. It returns facts and quotes; it never edits files and never spawns agents of its own. Never delegate reading of the repo's docs, the phase plan, code, or the diff under review — do that reading yourself, in this session."
4. **Reviewer isolation:** the reviewer's prompt is `notes/REVIEW_PROMPT.md`'s contents with `{PHASE}` substituted — **nothing else**. Never add your own summary or framing of what was implemented; the cold read is why review 2 finds what review 1 doesn't.
5. **Author-only calls** (full list in the CLAUDE.md amendment) are never made by you or a subagent. Log them to `notes/QUESTIONS.md` and surface them in the checkpoint report; escalate mid-phase only if the phase is blocked without an answer.
6. **Don't re-verify green work.** If the implementer reports the suite green with counts, don't re-run it; spot-check only when a report is ambiguous or contradicts something you can see. Your own turns are part of the token budget.

## The phase loop

**0. Preflight — know the whole picture.** Read, in full: `CLAUDE.md`, `notes/CoreDescription.md`, `notes/OverallModel.md`, `notes/AppSpec.md`, `notes/SyncSpec.md`, `notes/DetailedPlanForPhases.md` (table, IN-FLIGHT table, closeout log), `notes/plans/workflow-transition-2026-10-06.md` (the tracker/PR/stage system), the board snapshot `~/dev/variorum/notes/TICKETS.md` (the frozen ledger it replaced is `notes/KnownIssuesArchive-2026-10-06.md`, cited by tickets by line number), `notes/QUESTIONS.md`, and the phase's plan file in `notes/plans/` (kickoff at top, steps, closeout section). For editor-adjacent phases add `notes/TEXTKIT2_NOTES.md`. This reading is not optional and not skimmable — you arbitrate spec disputes later, and you can only do that from the whole picture. Then: identify the effort (the argument per "Resolving the argument" above, or the in-flight table); verify the previous closeout exists (it is your baseline — do not run the test suite to "check"); surface any unanswered blocking question from `notes/QUESTIONS.md` to the author now. If the phase needs the author at the start (Phase 5: Supabase project + credentials; anything needing Xcode GUI/signing), confirm with her before spawning anything.

**1. Implement.** Spawn the implementer (the `opus-implementer` agent type, or as the author redirected at kickoff) with: the phase plan's **kickoff message verbatim** (the blockquote at the top of the plan file), plus the *implementer addendum* below. It executes the plan's steps, runs tests at the end of steps/phase, does its self-review, and writes the closeout section of the phase plan file.

**2. Check.** From its report confirm: closeout written into the plan file, tests green with counts, PROVISIONAL calls listed, commits made per convention (schema/model commits separate). Do not re-run green suites (rule 6).

**3. Cold review.** Spawn the reviewer per rule 4 (`fable-reviewer`, or `opus-reviewer` where rule 2's scope test allows it). It returns a severity-ranked findings list + clean bill.

**4. Adjudicate.** SendMessage the findings **verbatim** to the implementer (it still has full context): for each finding — *agree* or *dispute* (rationale grounded in AppSpec/OverallModel/SyncSpec/plan). **Same-model phases (implementer and reviewer on the same model):** you arbitrate disputes against the canonical docs; the spec wins; the implementer applies the agreed fixes. **Cross-model phases (Fable reviewer, non-Fable implementer — author flow, 2026-07-07):** you do NOT arbitrate. SendMessage the implementer's responses back to the reviewer, which makes the final call on every finding (a dispute is a reason to recheck, or to dismiss as wrong; the spec outranks both agents) and then **implements the fixes for its confirmed findings itself, in its own session** — authorize this explicitly in that message (its review prompt bound it read-only until you do). After its fix pass: require the full suite green with counts, then give the implementer one SendMessage pass over the reviewer's diff (it holds context the reviewer doesn't; anything it raises goes back to the reviewer for the final word). Either way: a dispute that turns on undefined product behavior is neither fixed nor dismissed — it goes to `notes/QUESTIONS.md`. **The review ladder (author, 2026-07-07):** round 1 (cold review) → fixes → round 2 (the reviewer RE-REVIEWS the fixes and what they touched — a real pass, not a confirmation); if round 2 surfaces any NEW BLOCKER/MAJOR, its fixes get round 3 (a full pass focused on those fixes). Hard cap three rounds — anything still open after that is recorded for the author, not looped on. **Every round's reviewer is a BRAND-NEW cold agent (author, 2026-07-07):** spawn rounds 2 and 3 fresh per rule 4 (REVIEW_PROMPT verbatim, zero framing) — the closeout's recorded findings/dispositions from prior rounds are their anchor; ensure the implementer has written those dispositions into the closeout BEFORE you spawn the next round. At most three reviewer sessions per phase, strictly sequential, never concurrent. **The hallucination guard applies to every fix (CLAUDE.md):** no fix without a self-traced concrete mechanism, and every bug-class fix lands with a red-on-old pin (fails pre-fix, passes post-fix) — a pin that can't fail on the old code exposes the finding as hollow; dismiss it with a written disposition instead of fixing it. Architectural/cleanliness findings need the traced mechanism and justification, not a pin.

**5. Record.** Every finding gets a written disposition in the phase plan's closeout (finding → agreed/disputed/deferred → what changed). PROVISIONAL calls and their options land in the closeout's ratify list AND `notes/QUESTIONS.md`.

**6. Closeout ritual** per CLAUDE.md, performed by the implementer, confirmed by you: results recorded in the plan file; master plan table + the effort's IN-FLIGHT row retired + one-paragraph closeout updated; the effort's board tickets closed or re-owned (no orphans); the PR merges to `main` as a MERGE COMMIT; **the author handoff written as the phase's LAST act** (`notes/handoffs/phase-NN-handoff.md` per CLAUDE.md — author checklist at the top, self-contained for a fresh session; if answering an author question would need this session's context, the docs are incomplete — fix them); **the next phase's execution plan written just-in-time in `notes/plans/` with a self-contained kickoff message at its top** (where a `phase-NN-brief.md` exists beside it, the brief's ratified decisions are binding on the plan); the superseded pointer, prior closeout paragraph and AppSpec §14's outgoing delta rolled into `notes/PhaseCloseoutArchive.md` / `notes/AppSpecDeltaArchive.md`; **the MOBILE PARITY line** (a row in `notes/MobileSoul.md`'s ledger, or the words "nothing mobile-visible" in the closeout paragraph); the build-debris tidy — delete this phase's `App/Variorum/DerivedData/<tag>/` walk/build folders (gitignored, ~1–2 GB each; unswept they reached 84 GB by 2026-10-01), **and once the PR has merged to `main`, ALL of the effort's run and walk evidence is deleted too** — walk screenshots, test and build logs, revert scripts, subagent scratch folders and scratchpad copies (her ruling at the 13x closeout, 2026-10-08: the plan file's record is the evidence of record; nothing else is kept). Keep only a folder a still-open effort uses, and only after confirming no build is running; commits per convention (NO attribution trailer; push per CLAUDE.md's push rule). Do not write the checkpoint report until the next kickoff exists.

**7. Checkpoint report — end your turn.** The handoff file from step 6 is the report's backbone — write the file FIRST, then post its substance in chat (the author reads the chat tonight and points fresh sessions at the file forever after). Lead with what shipped and the test counts in plain prose a reader with no session context can follow. Then: (a) the **ratify list** — every PROVISIONAL call and interpretation, each with the options considered and what was picked; use AskUserQuestion for decisions with clear options, prose for open-ended ones; (b) review dispositions worth her eyes (anything disputed, deferred, or surprising); (c) author-only items queued in `notes/QUESTIONS.md`; (d) what the next phase is and what, if anything, it needs from her at its start. No invented shorthand — she reads this cold.

## Implementer addendum (append to every kickoff message)

> **Autonomous mode.** Where the spec/model is ambiguous and it does NOT gate the phase's core: write the 2–3 options into the phase plan's closeout notes, implement the most spec-defensible one, mark it **PROVISIONAL**, and append the question to `notes/QUESTIONS.md`. If the ambiguity gates the phase's core, stop and report back instead.
> Never, under any circumstances: invent product behavior; violate or relax an invariant (I1–I10, P1–P3, S1–S5); add a new third-party dependency; contradict the canonical docs (record deltas in the closeout instead); touch anything requiring the author's accounts or credentials; delete or overwrite anything the author created; rewrite history or force-push (plain pushes per piece are REQUIRED — the resiliency protocol). Those are author-only calls — log to `notes/QUESTIONS.md` and report.
> Do not spawn subagents or use the Agent tool, with one exception: you may run at most ONE Sonnet lookup subagent at a time (spawn it with `model: \"sonnet\"`), strictly for external facts — web searches, Apple documentation, API signatures/availability. It returns facts and quotes; it never edits files and never spawns agents of its own. Never delegate reading of the repo's docs, the phase plan, code, or the diff under review — do that reading yourself, in this session.
> Report back with: what shipped, test counts, PROVISIONAL calls made, commits made, anything requiring the author. Write the phase plan's closeout detailed enough to be reviewed against the spec — a cold reviewer will do exactly that.

## Escalate immediately, mid-phase

Don't wait for the checkpoint if: the phase is blocked on an author-only call; the implementer and reviewer deadlock on a spec reading; anything destructive outside the repo is proposed; a performance gate (P1-class benchmark, Phase 6 TK2 gate) fails — adjudication is the author's; or anything smells wrong enough that you'd rather stop early. Stopping earlier than planned is always allowed; later never is.

## Resuming

State lives in the docs, not in your context: the master plan's pointer + closeout log, the phase plan files, `notes/QUESTIONS.md`. A fresh `/run-phase` picks up exactly where the last one stopped. If a previous run died mid-phase (closeout missing, work half-committed): assess from `git status`/`git log` and the plan file, then spawn a fresh implementer with the kickoff plus a one-line note that partial work exists and must be verified before continuing — never assume it's correct, never redo it blind.
