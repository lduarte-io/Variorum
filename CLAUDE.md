## Product principles
OverallModel §1–6 (loaded above) is the text: the block is the atomic unit, rows-as-truth through the operations API, mutation ephemeral and permanence append-only, coarse not forensic, cost ∝ viewport. Invariants I1–I10, P1–P3, S1–S5 are enforced by pure domain rules and DB constraints, never by views; relaxing one is an author-only call.

## Architecture
SwiftUI + Observation + swift-dependencies (no TCA); the editor core is a TextKit 2 `NSTextView`; SwiftUI does all chrome.
- One feature = one self-contained module under `App/Features/`, composed at the app level (`RootView`). Cross-feature interaction routes through parent composition; the prohibition binds STATE AND OWNERSHIP, never rendering — a feature never constructs, holds or calls a sibling's view model (that destroys testability), while rendering a sibling's view is legal. A view consumed by two features moves to the shared home (`Core/Views/` Mac-only, `App/Variorum/Shared/` cross-platform) at the next touch.
- View models are `@Observable`, hold projections and IDs (never copies of persisted text), and call operations — no business rules or side effects in them. Views render state and send actions.
- Persistence and side effects live in injected dependencies (`@Dependency(\.database)`, `\.date`, `\.uuid`) so IDs and timestamps are deterministic under test. No global singletons; a long view model is mixing concerns — split it.
- Domain rules (invariants, churn, snapping, segmentation, joins) are pure functions in `VariorumCore/Domain`, tested independently.
- TextKit 2: opt in explicitly; never touch TK1 APIs (`.layoutManager` silently downgrades); keep the fallback canary; decorations off the live storage; attribute stamps clamped to the verdict's range.
- Sync is settled (SyncSpec): a dumb server, client-side merges; every phase honors the schema's sync machinery (`sync_version`, outbox triggers, fractional positions, tombstones). Triggers own only tombstone propagation and outbox capture.
- If something feels complex it is probably wrong — a tortured operation means the schema is wrong. Every action traces to a spec section.

## Build workflow
- `notes/DetailedPlanForPhases.md` is PRODUCT ADVANCEMENT ONLY: the phase table, the IN-FLIGHT table (one row per concurrent effort), the latest closeout paragraph. `notes/plans/` holds one execution plan per phase, self-contained for a fresh session, written just-in-time one phase ahead.
- Bug fixes and tech debt never go in the master plan: **they are VX tickets on the Linear board** (the lettered-ledger era is CLOSED — no new letters ever; the ledger files are archives of their run records). Pin before fix binds. An Opus cold review is mandatory per fix, a Fable one whenever the diff touches `Sync/`, custody/keychain or the editor seam; the author may waive it. **A small fix's record is its PR + a commit message stating the traced mechanism and the pin**; a fix that runs a ladder or touches `Sync/`/custody/the editor seam still lands a repo record file (`notes/plans/fixes/vx-NNN-<slug>.md`).
- Deferred work is a ticket too: every ticket carries a project or an explicit Parked state WITH a reason — unowned/reason-less ⇒ fix it now. `notes/KnownIssuesAndTechDebt.md` is absorbed into tickets (the record: `notes/plans/workflow-transition-2026-10-06.md`); `notes/TICKETS.md` is the generated board snapshot (`Tools/vx sync` at bout start — never hand-edit it).
- Sizing (guidance to raise — `notes/PhaseSizingGuidance.md`): the unit of work is an ACCEPTANCE UNIT verified by evidence of its kind (use, a live round, a drill, state-transition tests); one unit per implementer session; at most two phase-sized units per phase; a batch closes only on use-shaped evidence, never a pin or mount smoke alone. A plan outside this says so to the author — never split or proceed silently.
- Schema/model changes get their own commit before the code that uses them; a synced schema change is a SyncSpec §12 lockstep event whose mirror deploy runs only on the author's explicit go.
- Closeout ritual, every phase: results in the plan file; master plan table + the effort's in-flight row retired + closeout paragraph (the outgoing ones roll into the archives); canon deltas applied exactly as ruled in the two-file shape above (the contract lines in place in AppSpec / SurfaceContracts; the dated entry and the narrative appended to `notes/AppSpecRecord.md`), then `Tools/canon-size` run and its line put in the handoff; the effort's tickets closed or re-owned; **every ticket the effort FILED is triaged before it closes** to the labeling rule under "Tracker & parallel work" below. The handoff lists the filed tickets grouped by priority; **the rulings reconciled — before the phase closes, re-read each ruling it built (especially wording like "every", "everywhere", "all") against what actually shipped, and ticket any remainder then**; the MOBILE PARITY line (a `notes/MobileSoul.md` ledger row, or "nothing mobile-visible"); the next phase's plan with a kickoff message at its top; LAST, the author handoff `notes/handoffs/phase-NN-handoff.md` — her checklist at the top, self-contained for a fresh session. Then the PR merges to `main` (merge commit), push, hard stop.
- `/Applications/Variorum.app` is the author's real-store daily drive (Xcode Run = Debug = the fenced dev store). Any Mac-app change ends by refreshing it at a zero-instance window: A1 safety copy of the store into the container's `Backups/safety-copies/`, `xcodebuild -scheme Variorum -configuration Release build`, copy to `/Applications`, verify codesign. Never quit or kill a running real-store instance.

## Tracker & parallel work (the record: `notes/plans/workflow-transition-2026-10-06.md`)
- **Linear holds status, sequence and numbering; the repo holds truth.** Two teams: **VX** (Mac/core) and **VM** (mobile — its own board and numbering; mobile epics mint there). A ticket body is a pointer + a one-liner, never a spec; a ruling born in a ticket lands in canon at the merge exactly as a sitting's would. Project = a phase/effort, its description pointing at the plan file. Orchestrator/planning sessions use the Linear MCP; implementers are briefed as ever and never need it; `notes/TICKETS.md` is the context-cheap snapshot.
- **Labeling a ticket:** ONE kind — Bug · Improvement · Feature · Debt · Exploration · Task (her own hands-on work, e.g. a device test) · Umbrella (a flagship, run ticket or epic — a phase ticket that IS the work stays Feature); on a Bug, Improvement or Debt, ONE Evidence label — Confirmed · Suspected · Test-only; ONE Area — Editor · Takes & Lenses · Library & sidebar · Books · Search · MCP · Castle & sync · Import & export · Settings & onboarding · App shell · Performance · Tests & tooling (an umbrella spanning the whole app takes none; label groups are single-select on this workspace); a Priority (Linear's field: Urgent · High · Medium · Low); Pre-launch if it gates launch — HER call per ticket, never inferred; Wording for a text-only fix; the "Needs Lillian" state while it waits on her call. **Never set an assignee** (only she and Claude work here). A small pre-launch bug she reports files as a child of the open pre-launch sweep ticket while one is open (VX-348 has run).
- **Keeping small tickets moving:** RIDERS — a run's kickoff checks the open Low and Medium tickets in the Areas it touches and offers them to her as riders, since a fix is cheapest while its code is open; SWEEP tickets — after launch a standing sweep ticket gathers small items and runs once it holds a run's worth; a PASS at every release — each open ticket is promoted, bundled into the next run, or closed with a reason.
- **Branches & PRs:** every build effort on its own ticket-named branch (`vx-123-slug`), merged to `main` by a PR titled `VX-123: …` — **merge commits only, never squash or rebase-merge** (canon cites commit SHAs). Build sessions never push `main` directly; the author's own doc commits stay legal. Ladder records stay repo-first; the PR is the merge vehicle.
- **A RUN bundles small tickets under one orchestrator** (`/run-phase vx-a vx-b …` — the phase skills resolve ticket ids and carry the full rule): one fresh RUN TICKET (`Run: <theme>`) whose number names the ONE branch and PR; members become sub-issues closing individually; record `notes/plans/fixes/vx-NNN-<slug>.md`; pin-before-fix PER MEMBER; the cold review covers the whole run's diff.
- **Parallel sessions:** one worktree per effort (`~/dev/variorum-<effort>`; `~/dev/variorum` stays `main`); kickoff declares the effort's surfaces and checks overlap against the in-flight table; at most ONE `Sync/`-or-custody-touching effort at a time; **closeouts serialize** (first-ready merges first, the next rebases); the shared ledgers (master plan, `notes/TICKETS.md`, `notes/QUESTIONS.md`, `notes/AppSpecRecord.md`) are touched only at merge moments, on latest main, by the merging session.
- **The stage (`Tools/stage`):** anything touching the screen or a shared store — GUI walks/cliclick, launching the Debug app, **EVERY `xcodebuild test` run (Mac app or simulator)**, dev-store resets, the `/Applications` refresh — requires a HELD stage claim (claims expire; stealing a live claim is the author's word). The test host IS the dev-store app: suites share real `UserDefaults` domains, post real pointer events, and the pointer-injection suites demand an idle machine — so app-suite runs are exclusive BY MECHANISM, not caution; simulator runs collide on CoreSimulator state the same way. Headless `swift build`/`swift test` on the core package never needs the stage and runs freely in parallel across worktrees. **The Air by convention isn't what runs suites, walks or flashing, and defaults to not running them — it does so only at the author's EXPLICIT say-so, never a full ban**; say-so work claims the Air's OWN lock (the lock is per-machine, `~/.variorum/stage.d`); the default road remains ssh to the Pro and the Pro's stage.

## Phase execution (two shapes)
`/run-phase` — spec-driven, the plan fully made; `/architect-phase` — feature/design-heavy, an architect mandate and author sittings (`.claude/skills/*/SKILL.md`). The author picks at each kickoff. Rules binding both:
- Preflight is mandatory and complete: this file and its auto-loaded canon, the master plan (incl. the in-flight table), `notes/TICKETS.md`, `notes/QUESTIONS.md`, the phase plan, `notes/SessionResiliencyProtocol.md`, `notes/SurfaceContracts.md`'s sections for every surface the phase touches, plus SyncSpec, TEXTKIT2_NOTES, MCPSpec and CastleRules whenever the phase touches their seams. Reading is never delegated.
- Cast: the orchestrator + ONE implementer + ONE cold reviewer at a time, strictly sequential; a fresh implementer per batch (context degrades sharply past ~500k tokens); a FRESH reviewer per ladder round; no fan-outs, swarms or extra verifiers. Implementer and reviewer may each run at most one Sonnet subagent at a time, for EXTERNAL facts only, read-only. Standing default: Fable orchestrates and cold-reviews (`fable-reviewer`), Opus implements (`opus-implementer`), both at xhigh; `opus-reviewer` where the diff has no editor seam, custody, `Sync/` or default's-meaning content. Any change inside `Sources/VariorumCore/Sync/` is Fable work. The author may redirect at any kickoff.
- Two reviews: the implementer's self-assessment, then a cold reviewer running `notes/REVIEW_PROMPT.md` VERBATIM with zero framing. The ladder: round 1 → fixes → round 2 re-reviews the fixes; a new BLOCKER/MAJOR earns round 3; hard cap three; findings and dispositions land repo-first before the next round. Same-model: the orchestrator arbitrates against the spec. Cross-model (Fable reviews, Opus implements): findings go to the implementer verbatim, its agree/dispute returns to the reviewer, which makes the final call; the IMPLEMENTER then applies the confirmed fixes (red-on-old per finding, the suite green), and the next round's fresh reviewer re-checks them — a final round's fixes, which no later round reads, get the orchestrator's line-by-line check against each finding. The reviewer implements a fix itself only for `Sync/` lines and for any finding it marks FINDER-FIXES (then one implementer sanity pass over its diff) — Fable's budget goes to finding and judging, not typing. Every finding gets a written disposition; a dispute on undefined product behavior goes to `notes/QUESTIONS.md`.
- Hallucination guard: no fix without a self-traced concrete mechanism; every bug-class fix lands with a red-on-old pin verified by revert; a pin green on both sides exposes the finding as hollow — record it, don't fix it.
- PROVISIONAL rule: ambiguity that doesn't gate the core → 2–3 options in the plan, build the most spec-defensible, mark PROVISIONAL, log in `notes/QUESTIONS.md`; ambiguity that gates the core → stop and report.
- One phase per invocation; hard stop; the author kicks off the next.
- Author-only, never made autonomously: inventing product behavior or changing canon beyond recorded rulings; relaxing any invariant or budget; adding a third-party dependency; anything needing her accounts, credentials or GUI steps; adjudicating a gate; deleting or overwriting anything she created; history rewrites and force-pushes.
