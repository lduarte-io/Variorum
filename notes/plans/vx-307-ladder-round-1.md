### MAJOR-1 · `App/Variorum/Shared/Protection/ProtectionCrossingActs.swift:181–185` (with `AppBootstrap.crossOnNewRoad`; the core's resume at `ProtectionOpenRoad.swift:472–478`) · Rule 11's export-off promise breaks silently when a Use Castle stops past its swap — the weekly plain-text export keeps running in Castle, with no notice, indefinitely

**(This is U2a's F-2, held for this round's severity call — CONFIRMED, judged MAJOR.)**

- **Mechanism (traced):** the app's only real scheduled export is the weekly `MarkdownInsurance` copy, driven by a defaults key (the `exportSwitch`). `cross` mirrors that switch into the sealed `DeviceSettings.scheduledExport` before the act, so the core's rule-11 step (`CommonSteps.swift:253`) turns the SEALED setting off and owes `.scheduledExportTurnedOff`; the app-side switch is then turned off ONLY in the in-process tail: `let exportTurnedOff = acted?.notices.contains(.scheduledExportTurnedOff) ?? false; if exportTurnedOff { followExportSwitch(...) }` (ProtectionCrossingActs.swift:184–185). If the act stops PAST its swap but BEFORE the export step (a crash, a kill, or any in-act error after the key lands — the catch at :177–178 falls through with `acted = nil`), the next open's settle resumes the plan core-side (`executor.settle` — its outcome is stringified into `report.settle`, a Diagnostics word; NOTHING on the new road reads the resumed act's notices) and turns the sealed setting off. End state, standing until a hand fixes it: the library is in Castle; the sealed setting says the export is off; the defaults switch is still ON, so `MarkdownInsurance` keeps writing every note, readable, on a timer — exactly what rule 11 exists to stop — and rule 11's "one notice you may reverse" is never spoken. (The non-crash form is the same hole: a past-swap in-act error returns `.made(door, exportTurnedOff: false)` at :191 and the switch is never followed.)
- **Why MAJOR, not BLOCKER:** the window needs a mid-act stop; the road is Debug-only until VX-329; the dev store is the only new-road store this phase. But this is the exact machinery VX-329 ships to Release, the failure is silent and standing (the only mitigation is U2c's Castle warning IF she happens to open Data Safety), and the fix is small. It should land in this ladder's fix leg, before VX-308 builds on the crossing road.
- **Red-on-old pin:** a planted crossing whose act stops past the swap before the export step (the crash-harness idiom on a planted road; the test bootstrap's own export suite `crossingTestExportSuiteName`), reopen through the road → assert the switch reads OFF (or the notice is owed to the reopened session). Red on this tree; green with the fix.
- **Fix shape (the implementer's):** reconcile at every `.ready` on the new road — when the opened library's record reads `mode == .castle` and the sealed `scheduledExport` is false while `exportSwitch.isOn()`, follow the switch off and owe rule 11's notice once (a receipt-class line, or set `RoadCrossingsModel.exportNotice` through the bootstrap). That one reconcile also repairs the related in-memory loss: today `RoadCrossingsModel.exportNotice` dies with the process, so a quit between the crossing and *OK* loses rule 11's notice the same way — state the reconcile's rule so both corners close together (the notice re-derived from "Castle + sealed-off + switch-just-followed", not held only in memory). If the implementer prefers surfacing the settle's notices instead, that also serves; the pin is the same.

### MINOR-1 · `Sources/VariorumCore/Protection/Wire/AccountVaultClient.swift:234–240` · `fetchVault`'s single-flight ignores `accountID` — a piggybacked caller can receive another account's snapshot

- **Mechanism:** `fetchVault(accountID:)` returns `fetchTask.value` whenever any fetch is in flight, without comparing the in-flight fetch's account to the caller's. Caller A fetches account X (the session's user — succeeds); caller B concurrently asks for account Y and receives X's `VaultSnapshot` instead of `VaultRefusal.notSignedIn`. Unreachable in today's composition (one bound account per scope, the executor's `requireSignedIn` belt above), but this is the production leaf VX-308's account faces will call from more places.
- **Pin:** headless, scripted `load`: start a slow fetch for X, concurrently `fetchVault(accountID: Y)` → assert it refuses `notSignedIn`. Red on this tree.
- **Fix:** key the in-flight task by account (or re-check `session.userID == accountID` before answering a piggybacked value).

### MINOR-2 · `Sources/VariorumCore/Protection/Wire/AccountVaultClient.swift:304–323` · the stale-challenge retry and the enroll road don't cover each other — the private `WireEnrollRequired.required` can escape to the caller untyped

- **Mechanism:** Swift catch clauses don't cover their siblings' bodies. Rare (an account's first-ever vault write racing a consumed nonce) but it is the one path where the leaf's typed-refusal contract leaks an internal token.
- **Pin:** scripted server — first update answers stale-challenge, the retry answers ENROLL → assert the thrown error is typed (today it is `WireEnrollRequired.required`). Red on this tree.
- **Fix:** restructure as a small loop (attempt → classify → at most one enroll + one fresh-challenge retry) so every exit is a typed refusal.
