## The binding principles (the 13b constitution, P-1…P-9 — copied per the `/architect-phase` skill; phase-specific names inside them are provenance, the rules bind)

- **P-1 — One capability registry.** Every user-facing act is declared exactly once: verb, scope
  (block/take/post/book), per-mode availability rule, its doors (menu / context / bar / shortcut /
  palette), and its refusal copy. Surfaces render their doors FROM the registry; gating is data,
  never per-view if-statements. A registry-walk test asserts every declared door exists and every
  rendered door is declared. This kills the D3/D4 class structurally — the capability matrix stays
  green by construction instead of by audit.
- **P-2 — Fire-and-DO (R115).** A rendered door either performs the act — including any mode-switch
  choreography, done visibly for the user — or delivers the operations layer's real refusal. A door
  that can never act in its context isn't rendered. Lecture-and-redirect is retired.
- **P-3 — One text surface, one liveness authority.** ONE TK2 surface component (live + read modes;
  one measurement brain — the width-gated remeasure; the shared canary) that every pane composes;
  the live editor core's identity machinery (`BlockRangeIndex`, crystallization) becomes its live
  mode, not a sibling implementation. "What text does this pane show, and is it live" is answered by
  ONE pure, unit-tested authority (`PaneTextAuthority`); views never re-derive it. Its invariants
  stated as code: exactly one live pane; the live pane is buffer-authoritative; read panes are
  projection-authoritative once caught up.
- **P-4 — Broadcasts carry signals, never decisions.** NotificationCenter may announce that
  something happened (mode changed, post opened); no listener derives business state or availability
  from a broadcast, and no flow's correctness depends on broadcast ordering. Cross-feature flows
  route through composition. (Stage 0's survey enumerates today's notification bus; Stage 1
  disciplines it.)
- **P-5 — The friction doctrine (R116).** Repeated pushback against a rule marks an
  under-architected feature. The response is never another patch: write the feature's DESIGN MEMO —
  intended behavior whole, edge cases enumerated on paper, refusal wordings, undo story — get the
  author's rulings on the product-flavored edges, then build to the memo. Happy path ships first,
  but the edges are *decided at design time*, not discovered by the author. First two memos owed:
  **merge** and **the W ceremony**.
- **P-6 — The tutorial is the executable spec (R113).** The guided tutorial flow is the contract for
  every happy path. It stays green — automated where the harness allows, screenshot-walked otherwise
  — and any change that breaks a tutorial step is a regression by definition.
- **P-7 — Find bugs before she does.** Every layer keeps a proactive harness: the ops-layer soaks
  (exist), the board/view-model invariant soak (Stage 1), the registry walk (P-1), the per-batch
  scripted screenshot walkthrough. Red-on-old stays absolute: no bug-class fix without a pin that
  fails on the pre-fix code.
- **P-8 — Standing law, consolidated.** P1–P3 performance invariants bind the rebuilt layer exactly
  as they bind the substrate (invalidation ∝ realized rows; one live editor; virtualized long
  views). Overlays, never rendering attributes. Chrome `fixedSize` texts always carry a `lineLimit`
  (the b6dae25 class). `Theme/VoiceControls.swift` is THE chrome vocabulary. Complexity lives in the
  store; restraint lives in the UI.
- **P-9 — No god objects in the frontend either.** A view model mixing board layout, text authority,
  and gesture routing splits by concern (`TakesViewModel` at 890 lines is the standing
  counterexample). Same hygiene rule as the substrate, applied where it was being waived.

## THE LAW AS BUILT — three pieces, and why each sits where it does

**1. The clamp is ONE pure rule** — `CrossBlockCompound.clampedToBlockText(_:ranges:)`,
`App/Variorum/Shared/EditorBrain/`. It trims one separator character off whichever edge sits on one.
Three things are stated at the line because a reader will otherwise re-derive them:

- **THE TAIL FENCE IS THE LOOP'S BOUND.** `i` runs `0..<ranges.count - 1`, so the LAST entry's
  `upperBound` — which is the open tail's separator when a tail exists — is never a candidate. The
  tail is not a block, so it is never a neighbour the run can absorb (the ruling's own fence).
- **THE ONE ASYMMETRY.** The LEADING trim additionally requires `ranges[i].length > 0`. A
  zero-length entry's position IS its predecessor's separator offset, and for a half-open span such
  an entry at `range.location` is INSIDE the span — she dragged from the blank line. Trimming there
  would drop the empty block out of her own selection. At the trailing edge the mirror is false (an
  entry at `upperBound` is not covered), so the trailing trim needs no condition. This is
  `BlockRangeIndex.wholeBlockRun`'s A8 fence, from the other side, verbatim in its reasoning.
- **BOTH TESTS READ THE ORIGINAL BOUNDS**, never the mutated ones, so a chain of empty blocks (whose
  separators sit exactly one apart) can never trim an edge twice.

**2. Shape (ii) — the trim — is FOUR LINES inside `plan`, and the shape of those four lines is the
whole design.** The RUN is still derived from the span SHE MADE (that is what decides which blocks
are in the selection, empty ones included); only the CONTIGUITY guard and the two intra-block CUTS
read the clamped span. Three consequences fall out for free, and each is worth naming:

- the existing `max(0, …)` / `min(length, …)` arithmetic already absorbed a one-character trim, so
  **the only thing that ever blocked these spans was the contiguity guard**;
- a block whose separator was merely trimmed **is not in the run** (it contributes no characters), so
  R-13u-1 cannot refuse a gesture that does not touch it — the cost option (c) was criticised for in
  #109 is not paid (cell 18);
- `CrossBlockRefusal.diagnose` walks the same raw-span run, so **the diagnosis and the plan still
  agree** with no change to `diagnose`'s geometry at all.

**THE COST, because P1 asks.** The clamp is ONE extra pass over the entry ranges, beside the two
`plan` already makes (`entryRanges()` and the run walk) — and it stops as soon as the separators pass
the span, so it is bounded by the span's position rather than always by the document. The standing
cost pins measured it on the same tree: `planCrossBlockEdit @8000 blocks — 2.12 ms`,
`crossBlockRefusal @20k blocks — 3.85 ms`, `separatorPair @20k — 8.14 ms`, all green. No new
allocation per keystroke either: the clamp runs only inside the gate's `.crossesBlockBoundary` arm,
which an ordinary keystroke never reaches.

## TRACE D-1 — ITEM 2, THE EAGER SPACE-EATER: the durability mint's edge trim

Her words: *"it's really annoying in both variorum and variorum mobile when you typed a space but

`trimmedPiece` strips the piece's TRAILING horizontal whitespace. So the mint's planned region
text differs from what is on screen by exactly the space she just typed, `finishMint` takes its
`normalized != tailText` branch, and:

```swift
programmaticReplace(region, with: normalized, blockID: nil, caretToEndIfWasAtEnd: true)
textView?.undoManager?.removeAllActions()
```

— her live text is rewritten under the caret, **and the text view's undo stack is cleared in the
same breath**, so ⌘Z cannot bring the character back either. Two seconds after typing a space,
mid-thought, the space is gone and there is no road to it. That is her report, exactly.

## TRACE D-3 — TRACE 1a: the read pane's foreign-string compare (RULING A-1's routing)
