### P4/P5 — VX-933: every door write off the cooperative pool

**The mechanism (traced on this tip, then made deterministic by P4).** `MCPServerHost.serve` (on the accept THREAD) starts each connection as `Task { await session.run() }` — a task on the cooperative pool, exactly `activeProcessorCount` threads wide (12 on the Pro). The door writes to a connection's socket with `MCPSocketTransport.writeAll`: a BLOCKING `write` loop that returns only once the kernel holds every byte — and an `AF_UNIX` stream pair holds 8 KiB each way (`net.local.stream.sendspace`/`recvspace`), a write to it waiting once 8,192 bytes sit unread (P5b's probe filled the pair at exactly 8,192), so any answer larger than 8 KiB waits on the CLIENT reading. Four roads wrote that way on a pool thread: (1) **the SDK's frames** — `MCPSocketTransport.send`, an actor method on the default executor, so a stuck frame held the actor's pool thread (later frames on the same connection queued as actor jobs, holding nothing — one thread per stalled connection); (2) **the over-cap answer** (`answerOverLimit`, the same actor); (3) **the opening's refusals** in `MCPSession.run` before the transport exists — the NUL-name refusal (VX-396), the key refusal and the store-error refusal, each `MCPShim.refusalResponse(toFirstLine:)` echoing the `initialize`'s id, which a client may make as long as the opening's 1 MiB line; (4) the opening's over-limit answer (fixed and small, but behind whatever the window wrote). A client that stops reading — paused, wedged, or hand-rolled — while such a write is pending held one pool thread for as long as it did not read. The host serves up to 16 connections (`sessionCap`), more than the Pro's 12-wide pool, so 13+ stalled clients stopped EVERY task in the app (the door, the database's async reads, every view model's work) until one of them read or the server stopped (a stop's `hangUp` shuts each socket down and the write fails). The other writes were already off the pool: the opening window's answers (the handshake's own thread), the over-session-cap refusal (`refuseOverCap`, its own thread), the close line (`sayClosing`, one non-blocking `send`).

**The shapes weighed (the fork rule).** (a) **A send timeout** (`SO_SNDTIMEO`) bounds the pool thread's hold, but a client paused past the bound loses its answer with a TORN frame (the write stops mid-line) and the SDK's error drops it — a new, wire-observable failure for a slow reader: NOT taken. (b) **The write off the pool** (the U1 record's `offPool` idiom, door-side — F-U1-2's own first shape): the same blocking write on a thread of the connection's own, the caller waiting suspended — same bytes, same order, same errors, the same session lifetime; nothing on the wire changes and the pool is never held: TAKEN. So the fork rule's STOP does not apply.

**Built** (`Sources/VariorumMCP/MCPSocketTransport.swift`, `MCPSession.swift` — no other file):
- **The connection's writer:** `MCPSocketTransport.writer`, a serial `DispatchQueue(label:)` per connection (a serial queue targets the overcommit root queue, never the cooperative pool's width — the U1 record's P-B finding is the precedent: its deadline timer moved to exactly this kind of queue). One per connection, so one stalled client never delays another's writes.
- **`written(_:)`:** the frame is handed to the writer INSIDE `withCheckedContinuation`'s body, which runs at once on the actor, before it suspends — so writes go out in the order the actor took them, which is the order they went out in when they ran on the actor; the writer runs `writeAll` under the same `writeLock` (VX-762's close-line discipline unchanged) and reads `errno` on the writing thread, where it was set (the old code read it after the lock — the same thread then; now it must travel). `send` throws exactly the error it threw. `answerOverLimit` (now `async`) goes through it too, behind any frame already handed over.
- **`disconnect` drains first:** `await drained()` (a no-op block through the serial writer) before its `shutdown` — so a `disconnect` still runs only after every write handed over before it has ended, exactly as when those writes held the actor and `disconnect` (an actor call) waited behind them. Without it, a session ending while a frame was stuck would shut the socket mid-frame — a torn line the client never saw before (R-933-D proves the guard reds).
- **`writeAllOffPool(_:_:)`:** a one-off write on a `Thread` of its own (the handshake's `openingOutcome` idiom), the caller awaiting; `MCPSession.run`'s four opening writes call it.
- **Unchanged, by design:** every byte and its order; every refusal's words; the close line (still one try-lock, one non-blocking send); the stop roads (a stop's `hangUp` still shuts the socket down, which fails a stuck write and lets its thread go — the threads are bounded by the session cap: at most one writer thread per connection is ever parked); `sessionCap`; MCPSpec's contract (no answer shape, close reason, drop road or sentence changes). The stuck write now parks a writer thread instead of a pool thread — for as long as before.

### P5b — VX-933: the fast road (timing parity) and the close line that never waits

**Why a second piece.** P6's whole-MCP-target runs on W4's first shape (`1304014c4`) reddened `MCPSetupKeyServerTests.twoToolsUnderOneNameAreToldApart` 3 of 3 (once at load 2, once with this unit's suite skipped): the raw connection's first line was `notifications/tools/list_changed`, BEFORE its `initialize` result. The diagnostic R-933-PRE-B (the pre-fix door, the same runs): 0 of 3. **The race is PRE-EXISTING** — the test has two prior sightings on pre-fix trees (VX-329's handoff, VX-502's F-A3) — and its mechanism (traced): the rebind writes the client's `setup_key_hash`, which the host's grants observation hears (`startObservingGrants` → `for session in live { await session.announceToolsChanged() }`); `announceToolsChanged` gates only on `declaredName != nil`, and the name is set in the SDK's `initialize` HOOK, before the result is sent — so an announce that reaches the new connection between its hook and its result's send puts the notification first. No possible wire order changed with W4's first shape, but every write paid a writer hop and a pool resume, which slowed the announce loop over the OTHER connections enough that the new connection's announce landed in that window instead of before the hook (where it is skipped). That is an observable shift in practice — a re-run setup's rebind (VX-198/VX-258) would more often show a client `list_changed` before its `initialize` result — so the shape was refined until the common case's timing is the old one. (The race itself is returned as finding F-W4-1, not built — a wire-order fix is MCPSpec's and hers.)

**The fast road** (`MCPSocketTransport.deliver` → `fastRoad`): while nothing of this connection waits on the writer (`handedOver == 0`) and the write lock is free, a frame is written on the actor at once — but only in steps the socket takes WITHOUT waiting (`writeWithoutWaiting`: `poll(POLLOUT)` with a zero timeout, then at most `step` bytes, the socket's send low-water mark `SO_SNDLOWAT` = 2,048, read once per transport by `writeStep`). XNU's send waits only while the free space is below both the write's length and the low-water mark; `poll` reports writable only while the space is at least the mark; only writes made under the write lock reach the socket meanwhile, and a client's reads only add space — so a step never waits. For a client that reads, the whole frame goes here, at the old timing (for the announce loop's tiny notifications, always). What the socket will not take now goes to the writer (`handOver`), and the frame is marked mid-write under the lock (`frameGate.midFrame`) until the writer — FIFO, so the rest is the first thing behind its start — writes it and clears the mark. While anything waits on the writer, every write goes behind it, so the order holds. The opening's one-off writes (`writeAllOffPool`) take the same fast road before their thread.

**A fact found on the way (probed — `scratchpad/w4/dontwait/probe{,2,3}.swift`, throwaway).** The first draft of the fast road used `send(…, MSG_DONTWAIT)`; the pool pins went RED again, 12 of 16. (`O_NONBLOCK` itself was not taken: it is a flag of the open file, shared with the reader thread's blocking `read`, whose loop reads `EAGAIN` as the end.)

**So VX-762's close line could BLOCK the stopping thread.** `sayClosing` sent the line with "ONE non-blocking send" (`MSG_DONTWAIT`). The stop's hang-up runs on whatever thread stops the server — `MCPDoor` is `@MainActor`, so her switch, the library closing and the lock road run it on the MAIN thread. To a client that stopped reading with whole frames unread (no frame mid-write, the lock free) and fewer free bytes than the line, the send waited — the app's main thread held until that client read. This is the same mechanism (a door write that waits on a client that stopped reading) at another face, folded in (**P-940-W4-3** — the orchestrator may split it to its own ticket): the line now goes only when the socket takes it whole without waiting — the lock tried, no frame mid-write (`frameGate`), the line no longer than the step, the socket writable — else it is DROPPED, which is its documented contract ("a socket buffer that can't take it whole tears or drops it"; the shim then says its own sentence).
