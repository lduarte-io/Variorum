### VX-132 — the trace (written before code)

**The symptom on record** (13n-b U3 ladder round 1, `notes/plans/13nb-u3-ladder-round1.md` ~l.307): one
`VariorumMCPTests` run never finished, the test helper at 100% CPU for 11+ minutes; `sample` showed "the SDK's
`Client.connect` message loop busy-spinning over `StdioTransport.readLoop`'s poll-sleep while
`MCPSocketTransport.readLines` sat in `read()`"; 13n-c met it three more times (killed, rerun green).

**The mechanism, read in the pinned SDK (swift-sdk 0.12.1, read-only) and then MEASURED:**
1. `Client.connect(transport:)` starts its message loop as `repeat { … let stream = await connection.receive();
   for try await data in stream { … } … } while true`. When the transport's stream FINISHES (the stdio read loop
   sees EOF — the server closed the socket), the `for try await` ends normally and the `repeat` comes straight
   back: `receive()` hands out the same finished stream, whose iterator returns nil at once — **a loop with no
   suspension that ever waits, forever**. Nothing cancels it but `Client.disconnect()`.
2. The same loop never fails the PENDING requests at EOF: `sendAndAwait` parks a continuation that only a
   response, `disconnect()` or a cancellation notification resumes — and `requestTask.value` ignores the caller's
   cancellation. **No request in the SDK has a time limit.** A call whose answer never comes waits forever.
3. The harness feeds (1) on every test: `ServerHarness.tearDown()` stops the host while the test's SDK clients are
   still connected (most tests never hang up; a refused `connect` never can — it threw), so every such client's
   loop spins for the rest of the test process.
   **Measured (a throwaway probe, never committed; each case its own `swift test` process):** three harness
   clients whose server then stopped, never disconnected → **6.37 CPU-seconds over 2 s of idle wall time** (one
   core each, for good); the same three disconnected first → **0.0002 CPU-s**. A whole `VariorumMCPTests` run
   leaves dozens of these spinning on the cooperative pool, so a later test's awaited answer is processed only
   when the pool can schedule it — and under (2) any answer that is lost or never sent is waited on forever.
   That is the sampled hang: a spinning loop beside a reader parked in `read()`.

**The fix shape (the harness only — the SDK is pinned exact and never patched, 13n-c §8):**
- **Hygiene — no client outlives its connection:** the harness hands the SDK a thin `HarnessTransport` (the SDK's
  own `StdioTransport` underneath, every call forwarded). When the client's message loop asks for the stream a
  SECOND time — which it does only once the stream has ended and every line in it has been handled — the
  transport parks the loop on a stream that never yields (no spin) and disconnects the client, which fails every
  pending request ("Client disconnected") instead of leaving it waiting. A server that closes now fails the call
  at once; the loop never spins.
- **Time limits (the ticket's ask):** `connect` and every `callTool` / `listTools` run under a deadline (default
  30 s per act, task-local so a pin can shorten it) whose timer is a GCD timer, so it fires whatever the awaited
  call does; on expiry the connection's socket is shut down (the transport reads EOF → the hygiene above ends the
  client) and the act throws a `HarnessFailure` naming itself — a hang becomes a bounded, named failure. The
  harness's raw `rawOpen` read gets a receive timeout of the same bound.
- **The pins:** a silent peer that never answers `initialize` → `connect` fails within its bound; a peer that
  answers `initialize` and then nothing → `callTool` fails within its bound (both HANG on the old harness — red
  watched under an outer watchdog); a connection the server closes → the client's message loop asks for its
  stream at most twice (red by reverting the hygiene alone: the count climbs without end).

### VX-132 — the SIGPIPE flake (found on the way, traced, fixed)

The FIRST whole-target run on the fixed harness died of **signal 13** (`swiftpm-testing-helper … exited with

SIGPIPE in 2 runs of 40**, both with `aKeyedShimSpeaksThePreambleFirstAndABareOneNothing` in flight. **The trace:**

even while the client keeps stdin open), and that thread's LAST act is `shutdown(socket, SHUT_WR)` once the client's
input ends. The test closed the input and then ended the downstream itself, so the shim thread could `close(pair[0])`

number back, the straggler shut THAT socket for writing, and the bare iteration's upstream write met a shut socket
with no `SO_NOSIGPIPE` — the whole test process died. (In the shipped shim the same straggler can only meet a closed
number between `close` and `exit`, with nothing opened in between — harmless; recorded, not changed.) **A kernel
fact measured on the way** (a Python socketpair experiment, scratchpad): once the peer has half-closed, macOS
answers `shutdown(SHUT_RDWR)` on an AF_UNIX pair with `ENOTCONN` and wakes NO blocked reader — only `close` does — so
the old test's `shutdown(pair[1])` also never ended its shim (it just never waited). **The fix (the test only):**
read `pair[1]` to EOF after closing the input (the upstream's `shutdown` IS that EOF — it is done), then `close`
(never `shutdown`) `pair[1]`, JOIN the shim thread, and only then close anything else; both pair ends carry
`SO_NOSIGPIPE`; every read is bounded. Assertions unchanged. **Evidence:** 80/80 runs clean after (2/40 SIGPIPE
before) — a timing race, so the red-on-old is statistical, said plainly.

### Over-cap answers — the argued shape (written before code)

**Today:** an OPENING line (the preamble, a window frame, the `initialize`) past `MCPHandshake.lineLimit` (1 MiB) ends

one read (64 KiB) can be served, and which happens depends on how the kernel chunks the stream. A boundary pin needs
the cap to be exact: a line longer than `lineCap` is over, whatever the chunking (the doc comment already says so).

### The design, argued (each member)

**VX-186 — the deduped shape: the block NAMES its shown take; the text lives once, on its take.** Each block loses its
block-level `text` and gains **`shown_take_id`** — the take this read shows there: the note's shown take (the one
marked `chosen: true`), or, under `lens_id`, the lens's take where `via: "lens"`. Every take keeps its own `text`, so
each text crosses ONCE; `chosen` keeps meaning the note's own shown take (VX-172's letter: a lens is a view), and
`via` keeps saying how the shown take resolved — `shown_take_id` is the id `via` was always describing. A block with no
live active take omits `shown_take_id` (nothing is shown). **Why this shape over the alternatives:** (b) keep the
block's `text` and drop the shown take's `text` — rejected: a take entry with no `text` reads as a BLANK take, which is
a legal take since R-VX171-2, so the shape would lie to a model; (c) mirror `create_note`'s input (the shown take's
id/label/text inline on the block, `takes` = the OTHER takes only) — rejected: the take's own facts (`label`,
`archived`, `commits`, `parent_take_id`) would then live at the block level beside the BLOCK's own facts (`name`,
`lineage`), two vocabularies in one object, and `takes` would stop listing every take; (d) per-block shapes (fanless
vs fanned) — rejected: a model must parse one shape. Cost of (a): one id (~50 bytes) per block instead of the shown
text. `create_note`'s description claims its blocks are "the same shape read_note's with_ids returns" — false under
(a) (and only half-true before), so that clause is corrected; `read_note`'s own description says the new shape.

1. **Every act = her op's row work + the grant guard FIRST inside the act's transaction + ONE client-named undo entry.**
   Canon (AppSpec §12: "Every write is one of §9's operations with the grant guard INSIDE the op's own transaction and ONE
   client-named undo entry") and the run's precedent (P-13nb-U2-4 — every MCP write registers one, "though some of her own
   doors — the tray's Put back, the date, the chapter filing, the rule — register none"; U3's `delete_comment` and
   `remove_tag` did the same) decide it: all twelve acts register ONE entry, including the ones her own doors leave off the
   stack (comment edits/restores, labels, locks, commit names, the title, the lens). The brief's "an act her own door makes
   undo-less stays undo-less" is VX-168 U2's argued case — a COMMIT, which has no inverse that would not destroy a row (I5,
   S2); none of U4's acts writes a commit as its act. The insurance savepoints two acts write on the way (`lock_take` on a
   dirty take — her op's own rule; `restore_commit`'s brackets) STAY when ⌥⌘Z walks the act back, exactly as `edit_take`'s
   brackets do (P-13nb-U3-2) — so the advice's "Every change you make is one undo for the author, named after you; commits
   stay." and the guide's lesson-1 promise stay true. PROVISIONAL **P-VX195-1** (options below).
2. **The edit rung's two decisions, every act** (AF-10 (a)): the snapshot (`onNote`, `spendsAfter: false`) speaks the
   refusal and raises the ask — the ONE not-shared answer for anything unreachable (a dead, foreign, version's or scraps
   id), `rungTooLow` + the asked sentence for a live holder below edit; the `WriteGuard` re-resolves the note from the act's
   own rows (the take, the comment, the commit's take, the lens) INSIDE the transaction, decides at EDIT, and spends any
   once grant there. A refused act spends nothing.
3. **`delete_comment` at EDIT (R-VX188-1's edit clause, in `mayDelete`):** the rung a delete needs is SUGGEST for a comment
   on file as this client's own, EDIT for any other. Snapshot: the note at suggest (unchanged — a read client hears the rung
   and an ask for suggest; unreachable is the one shape); then a comment not on file as its own needs EDIT on the note, else
   her ruled sentence, byte-unchanged (suggest and write-new callers alike; still no ask — P-VX188-1). The guard decides the
   needed rung on its own rows and spends exactly that rung's once grant — never two.
4. **`edit_comment(comment_id, text, expected_text)`** — `expected_text` REQUIRED, `edit_take`'s discipline for replacing
   text she wrote (R-13n-7's class; a stale read refuses and writes nothing) — PROVISIONAL **P-VX195-2**. The authorship
   record is untouched by an edit (it says who WROTE the comment). The undo puts the old text back only while the comment
   still reads the act's text (an edit of hers since is hers — quiet), the redo likewise.
5. **`delete_take` — the LAST take deletes the BLOCK (R-VX184-1):** "last" is I10's — the take is ACTIVE and its block has
   no other live active take. Then the act is `delete_block`'s exactly (the block and every take — archived ones too — go to
   the tray, `deleteBlock`'s undo entry relabeled "‹client›'s delete", the receipt "deleted a block (its last take)", the
   answer `deleted_block: true`, Activity logs the BLOCK). Otherwise `deleteVariant` exactly (its refusals: a CHOSEN take —
   choose another first, as at her keyboard; a seal). The ROAD is chosen on the snapshot and RE-CHECKED inside the
   transaction (a take that stopped or started being the last since the read refuses whole, nothing written — the
   compare-and-set class). A LOCKED take refuses on BOTH roads (the lock guards the take; `delete_block` stays the explicit
   road for a block) — PROVISIONAL **P-VX195-3**.
6. **`restore_commit(commit_id)` — INSURED:** the eighth occasion's bracket — a quiet commit "before ‹client›'s restore" of
   the text it replaces and "after ‹client›'s restore" of the restored text (+1 ms), each deduped by the standing rule —
   then her `restoreCommit` row work (refusals, no-op, churn exactly hers). Why both brackets: the replaced buffer is what
   becomes unreachable after the session (OverallModel §3's doctrine), and the guide's lesson 3 promises "When it changes a
   take, Variorum commits the take just before and just after". The undo restores the pre-restore buffer exactly
   (`revertStructural` with insurance — the fourth occasion for a buffer she edited since), the redo the restore again.
   PROVISIONAL **P-VX195-4**.
7. **`rename_commit(commit_id, message)`** — her `renameCommitPoint` semantics exactly (nil/blank clears; a no-op writes
   nothing; the SEAL checked FIRST; allowed on a locked or archived take — QUESTIONS #121); the message stored AS GIVEN

8. **`archive_take` / `unarchive_take` / `lock_take` / `unlock_take` are FOUR tools, not two with a boolean:** her menu's

   Unarchive door; without it the client's archive is one-way except by her ⌥⌘Z) — PROVISIONAL **P-VX195-6**.
9. **`set_take_label`, `rename_note`** — as given (her doors' semantics: nil/blank clears, trimmed), no client stamp

10. **`delete_lens(lens_id)`** — her `deleteLens` (a tombstone; its choices die on its stamp); the undo revives the lens

11. **`restore_comment(comment_id)`** — her restore door's population: a DELETED comment on her block's deleted-comments
    surface (`Queries.deletedBlockComments`' predicate — a comment given "Delete forever…" refuses, never a door her surface
    doesn't offer: `put_back`'s tray rule), its block live and placed in a note the client may EDIT. The wire has no read of

    read or the client's own delete. The undo deletes it again (a fresh stamp), the redo revives it on the undo's exact stamp.
12. **Private / Seal / Own stay HERS ALONE** (R-VX184-2): no tool here touches `ai_private_at`, a post's seal
    (`lockPost`/`unlockPost`) or `owned`; `lock_take` is the TAKE's lock (her per-take guard), never the note's seal.
13. **Wording** — every description, refusal, receipt, Activity phrase and undo label ships AS BUILT: **P-U4-WORDS** (her
    copy pass; the QUESTIONS road — not VX-234, which is the pane's wording review).
