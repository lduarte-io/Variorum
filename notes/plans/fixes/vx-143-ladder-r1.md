## Findings

### MAJOR-1 · `App/Variorum/Variorum/RootView.swift:709–728` (with `:670–689`; `BookView.swift:363/379–384/988–1004`) · VX-141's held slot can stand a PHANTOM empty note box indefinitely under a focused Read-mode book in a split

**What's wrong.** The new held-slot fallback shows the box's empty face whenever the focused pane shows a book whose report is absent, and the only thing that suppresses it is `noteBoxDeclinedBy` — ONE book id. But a book only speaks through `publishNoteBox()` from `.onAppear` and `.onChange(of: noteBoxReport)` (`BookView.swift:363, 379`), and for a Read-mode book the computed report is nil **regardless of pane focus** (`BookView.swift:991`: `guard paneFocused, BookNoteBox.shows(mode: structure.mode) else { return nil }`). So a pane-focus change on a mounted Read book is nil→nil — `onChange` never fires, the book never re-speaks its "no box" word, and the declined bookkeeping (`RootView.swift:676–685`) is never consulted for it.

**The traced mechanism (inputs → wrong state).** A split (13f W1/A25 — `WorkspaceModel.panes`, two panes real): pane 1 = book A in Read, focused (its `.onAppear` nil, published while focused, sets `noteBoxDeclinedBy = A` — or A's word is later cleared by its own focus-loss ordering; either way the word is not B's); pane 2 = book B in Read, mounted while pane 1 held focus, so B's `.onAppear` nil arrived with `focusedReadingID == A` and was treated as a departure (`RootView.swift:680–681` clears only if the word was B's — B never gets a word). She clicks into pane 2: `focusedReadingID = B`; `noteBoxReport` is nil; `noteBoxDeclinedBy (A or nil) != B` → `RootView.swift:726` returns `SidebarNoteBox(state: .empty)` — and **nothing will ever replace it**: B is mounted (no `.onAppear` coming), B's report stays nil→nil in Read, and no other channel reaches `adoptNoteBox`. A permanent "no note selected" box stands in the sidebar under a Read book — where the 18d contract's own words are "nil ⇒ nothing to show: Read" (`BookView.swift:988`) and where the pre-diff tree showed none. The same phantom can arise on simply OPENING a split onto a Read book when the new pane's focus lands after the book's `.onAppear`.

**Why it is MAJOR, not blocker:** a corner configuration (split + Read + focus order), chrome-only, no data or invariant at stake — but it is a standing wrong face that directly contradicts the pane's ruled "Read shows no box" word, introduced by this diff, and it is permanent once entered (not the transient held pass the fix intends).

**The pin that proves it (red on THIS tree, green on old and after the fix):** a hosted `RootView` with two panes, both `.reading` selections, both books driven to Read; focus flipped to the second pane; assert through `SidebarGeometry` that no box frame is recorded for book B / the slot's occupant sequence never settles on `.box` while B is the focused Read book. On the pre-diff tree the slot simply shows nothing (green); on this diff the empty box stands (red).

**Proposed fix (smallest honest one):** make the "no box" word reach RootView on pane-focus changes — `BookView`'s `.onChange(of: paneFocused)` (`BookView.swift:357`) also calls `publishNoteBox()`. A Read book then re-speaks nil the moment its pane takes focus (`focusedReadingID == bookID` → `noteBoxDeclinedBy = bookID` → no phantom), and an editing-mode book re-publishes its report, which is what the `onChange(of: noteBoxReport)` road already does today. (The alternative — a per-book declined SET — does not close the hole by itself, because B's only nil arrives while unfocused and is indistinguishable from a departure on the current one-channel publish.)
