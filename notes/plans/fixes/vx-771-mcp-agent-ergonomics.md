## Binding principles — the 13b constitution (copied per the architect-phase skill; byte-verbatim from the skill's text)

- **P-1 — One capability registry.** Every user-facing act is declared exactly once: verb, scope (block/take/post/book), per-mode availability rule, its doors (menu / context / bar / shortcut / palette), and its refusal copy. Surfaces render their doors FROM the registry; gating is data, never per-view if-statements. A registry-walk test asserts every declared door exists and every rendered door is declared. This kills the D3/D4 class structurally — the capability matrix stays green by construction instead of by audit.
- **P-2 — Fire-and-DO (R115).** A rendered door either performs the act — including any mode-switch choreography, done visibly for the user — or delivers the operations layer's real refusal. A door that can never act in its context isn't rendered. Lecture-and-redirect is retired.
- **P-3 — One text surface, one liveness authority.** ONE TK2 surface component (live + read modes; one measurement brain — the width-gated remeasure; the shared canary) that every pane composes; the live editor core's identity machinery (`BlockRangeIndex`, crystallization) becomes its live mode, not a sibling implementation. "What text does this pane show, and is it live" is answered by ONE pure, unit-tested authority (`PaneTextAuthority`); views never re-derive it. Its invariants stated as code: exactly one live pane; the live pane is buffer-authoritative; read panes are projection-authoritative once caught up.
- **P-4 — Broadcasts carry signals, never decisions.** NotificationCenter may announce that something happened (mode changed, post opened); no listener derives business state or availability from a broadcast, and no flow's correctness depends on broadcast ordering. Cross-feature flows route through composition. (Stage 0's survey enumerates today's notification bus; Stage 1 disciplines it.)
- **P-5 — The friction doctrine (R116).** Repeated pushback against a rule marks an under-architected feature. The response is never another patch: write the feature's DESIGN MEMO — intended behavior whole, edge cases enumerated on paper, refusal wordings, undo story — get the author's rulings on the product-flavored edges, then build to the memo. Happy path ships first, but the edges are *decided at design time*, not discovered by the author. First two memos owed: **merge** and **the W ceremony**.
- **P-6 — The tutorial is the executable spec (R113).** The guided tutorial flow is the contract for every happy path. It stays green — automated where the harness allows, screenshot-walked otherwise — and any change that breaks a tutorial step is a regression by definition.
- **P-7 — Find bugs before she does.** Every layer keeps a proactive harness: the ops-layer soaks (exist), the board/view-model invariant soak (Stage 1), the registry walk (P-1), the per-batch scripted screenshot walkthrough. Red-on-old stays absolute: no bug-class fix without a pin that fails on the pre-fix code.
- **P-8 — Standing law, consolidated.** P1–P3 performance invariants bind the rebuilt layer exactly as they bind the substrate (invalidation ∝ realized rows; one live editor; virtualized long views). Overlays, never rendering attributes. Chrome `fixedSize` texts always carry a `lineLimit` (the b6dae25 class). `Theme/VoiceControls.swift` is THE chrome vocabulary. Complexity lives in the store; restraint lives in the UI.
- **P-9 — No god objects in the frontend either.** A view model mixing board layout, text authority, and gesture routing splits by concern (`TakesViewModel` at 890 lines is the standing counterexample). Same hygiene rule as the substrate, applied where it was being waived.

#### VX-762 — B2 (P-771-3): the trace of the pump, part one's design, PART TWO PROPOSED (before any part-two code)

**The pump today** (`Sources/VariorumMCPSocket/MCPShim.swift`): `serve` writes the setup key's preamble, then `pump` runs two `copy` loops — `input → socket` on a helper thread (its end half-closes the socket, `SHUT_WR`, so the app sees the session end) and `socket → output` on the calling thread, each `read` of up to 64 KiB written verbatim with no notion of lines. The run ends when the downstream `copy` returns (the socket's EOF or error, or a failed write to stdout); `main.swift` then exits 0. Nothing is ever said on stderr for a pumped run — so a client sees only "MCP server disconnected" (the VX-394 trace's shape), and nothing says Variorum did it.

**Part one (unconditional — the brief's sentence, PROVISIONAL words):** when the APP ends the socket — the downstream's READ side ended (EOF or error) and the client's input had NOT ended first — the shim writes ONE line to stderr: "Variorum closed the connection — reconnect with /mcp once it's back." Nothing when the client ended first (its stdin's EOF → the half-close → the app's answering close: the flag is set before the `shutdown`, so the answering EOF always finds it) or when the client's stdout failed (nobody is reading). The upstream sets "the client's input ended" only when its copy ended on the SOURCE side (stdin's EOF), never on a failed write to the socket (the app's close seen first from that side). `errorOutput: Int32 = STDERR_FILENO` joins `run` / `serve` / `pump` (defaulted — every caller and `main.swift` byte-unchanged; the test passes a pipe). Red on old: by BEHAVIOURAL REVERT of the one write (record-first; the pins call the new parameter, so they cannot compile on the pre-change tree — the batch 1 VX-765 method).

**Part two — the close reason (PROPOSED here; built only if it stays MCP-blind by construction):**

- **The shim — where line awareness enters.** The downstream `copy` becomes a `relay` with ONE state bit, `atLineStart` (true at the stream's start and after every `\n` byte, carried across reads), and a capped divert buffer. Same 64 KiB reads; each chunk is scanned for `\n` (`firstIndex(of:)` — linear, the app's own `readLines` cost); a line whose FIRST byte is **0x1E** (ASCII RS) is the app's CLOSE LINE: its bytes up to (excluding) its `\n` go to the divert buffer (512 bytes kept, the rest dropped) instead of stdout; every other byte goes to stdout verbatim, in order, as contiguous spans. One byte at a line start decides — no lookahead, nothing held back from stdout, nothing parsed. At the app's end, the ONE stderr line is the close line's words (the 0x1E stripped) when it arrived COMPLETE (its `\n` seen) and reads as UTF-8 with no control characters; otherwise part one's sentence. Still one line per drop.
- **Why no legitimate byte sequence can collide.** (1) Every line the app writes on the socket is a JSON text — the SDK's `JSONEncoder` frames, `JSONSerialization`'s refusals and the handshake window's answers — and a JSON text cannot contain the raw byte 0x1E ANYWHERE: RFC 8259 §7 requires U+0000–U+001F to be escaped inside strings, and outside strings only structural characters, the literals, numbers and the four whitespace bytes (0x20 0x09 0x0A 0x0D) are legal. (2) UTF-8 never uses a byte below 0x80 inside a multi-byte sequence, so 0x1E is only ever U+001E itself. (3) MCP's stdio framing is newline-delimited with no embedded newlines (MCPSpec's A-3: the socket's framing IS stdio's), so a line start is a frame start; a close line ends at its own newline, so it can never swallow a frame. Even a line-tracking slip could only ever divert a line that starts with 0x1E.
- **Why the shim stays MCP-blind.** It reads no JSON and knows no method: newlines (A-3's framing — already the shim's contract) and one byte that is never JSON — the downstream twin of VX-168's one preamble line upstream. Compatibility by construction: the shim ships inside the app bundle and a connection's shim process is always the serving app's own version (the setup points at `Contents/MacOS/variorum-mcp`; an update quits the app, which ends every connection and so every shim), so no older shim ever receives a close line (one would forward it to stdout — a single non-JSON line just before EOF).
- **The server — inside the existing hang-up step, order untouched.** `halt`'s per-session `ending(session); session.hangUp()` becomes `ending(session); session.hangUp(saying: line)`: the close line, then the SAME synchronous `shutdown(SHUT_RDWR)` (VX-369 row 4's dependency kept — every connection is shut before the pool closes). No step added, moved or reordered in `halt`, `MacWillLock.swift` or `AppBootstrap.swift`; `recordConnectionEnds` and every Activity line untouched.
- **Never mid-frame, never blocking a stop.** The transport's frame writes (`send`, the over-cap answer) take a write lock (`NSLock`) around their `writeAll`; the close line takes it with `try()` — never waits — and goes out in ONE `send(…, MSG_DONTWAIT)`. A frame mid-write (the lock held) or a socket buffer that can't take the line whole skips or tears it, and the shim — which honours only a COMPLETE close line — says part one's sentence. A connection still in its handshake (no transport yet) gets none.
- **The words (PROVISIONAL, her copy pass; one per stop that has a reason):** her switch OFF — "Variorum's MCP server was turned off, so it closed this connection — reconnect with /mcp once it's on again." · the lock road and every store close (`.libraryClosed`) — "Variorum's library locked or closed, so it closed this connection — reconnect with /mcp once it's open again." · the quit — "Variorum quit, so it closed this connection — reconnect with /mcp once it's open again." (P-VX394-5's "a quit logs nothing" is the Activity log's and stands). A client's own close, the over-cap answer and the session cap's refusal are not stops: no line.
- **Pins:** the relay pure over pipes (a close line diverted whole, every JSON byte verbatim across arbitrary chunk splits, a torn close line falls back, a 0x1E inside a line passes through, nothing diverted without the byte); the server end to end over a real socket (each stop road's line reaches a raw reader as the stream's last line before EOF; a session mid-handshake gets none); and the shim on a real session (the lock road's words on the stderr pipe, stdout's frames byte-identical).
- **Cost:** the shim — one scan per chunk; the server — an uncontended lock around each frame write and the session holding its transport. **The read: it stays byte-blind cheaply → build it** (after part one), unless the orchestrator rules otherwise.
