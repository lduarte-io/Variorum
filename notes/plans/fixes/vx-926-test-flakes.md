### The upstream facts (one read-only Sonnet lookup, external sources only; quoted, with the source named — not re-verified line by line here)

- **The modes** (ST-0021 "Targeted Interoperability between Swift Testing and XCTest", Implemented in Swift 6.4 — `swiftlang/swift-evolution` `proposals/testing/0021-…md`; Apple's "Migrating from XCTest" table): `none` — "Interoperability is off. Swift Testing and XCTest ignore cross-library issues."; `limited` — XCTest issues become warnings plus modernization hints (Phase 1's headless table shows exactly this: "Test «unknown» recorded a warning … Replace XCTest API such as 'XCTAssert'…"); `complete` — cross-library issues keep their severity; `strict` — XCTest issues `fatalError()`. Xcode: "Test plans created before Xcode 27 inherit limited mode … For new projects, Xcode uses the complete mode" (WWDC26 #267). The proposal is SILENT on an issue recorded with no test running in either library — the gap this loop lives in.
- **Where the loop is, in the open-source Swift Testing** (`Sources/Testing/Events/Event.swift`, main `99cd1683` and the swift-6.4.0 / 6.4.2 release tags): `Event._post` hands an event to the fallback handler only when there is no current configuration AND `Configuration.all` is empty — no Swift Testing run active — which is Phase 1's timing finding, now from the source. `Event+FallbackEventHandler.swift`'s `_postToFallbackEventHandler` has two guards only: `Interop.Mode.current != .none` (swift-testing PR #1743, merged 2026-06-05, in 6.4.0) and "the fallback event handler belongs to Swift Testing" (an address check). **No re-entrancy guard** — XCTest's handler has another address, is called, and re-enters `Issue.record`. (Release 6.3's `postToFallbackHandler` had neither guard.)
- **The XCTest side:** the open-source swift-corelibs-xctest DROPS an issue when no test case is current and the fallback handler is XCTest's own ("This prevents us from getting into a recursive 'error handling loop'"); Xcode's closed XCTest instead forwards it into Swift Testing (`SwiftTestingInteropRecordHandler.handleIssueRecorded` → `Issue.record`, in every one of our 24 stacks). That asymmetry is the bug report.
- **The entry, on Point-Free's side:** swift-issue-reporting's `TestContext.current` answers `.xcTest` whenever `isTesting` is true and no Swift Testing test is current, without checking for a running XCTest case, so `_DefaultReporter` calls `_XCTFail` — frames 105–107 of every stack. swift-dependencies' documented answer ("Testing gotchas ▸ Testing host application": skip the app's entry when `isTesting`) is what VX-604 built.
- **Prior reports:** none found — no swift-testing / swift-corelibs-xctest / swift-issue-reporting issue or PR, no Swift-forums thread on this recursion (Apple's own forums and Feedback could not be read). Nearest relatives: swift-testing #1542/#1543, #1743; corelibs-xctest #538, #542.
- **The test-plan key** (undocumented in prose; seen in real files): `.xctestplan` `defaultOptions.testInteropMode` (a string, e.g. `"complete"`); `.xctestrun` `TestInteropMode`.

### PHASE 1 — the trace (what starves, with the evidence)

**What starves: the cooperative pool's QUEUE, not GRDB, not the reader pool, not the stream's buffering — and nothing circular.** A held `AsyncValueObservation` (GRDB 7.11's `values(in:)`, the default `.task` scheduler) reaches its test through two cooperative-pool hops: (1) GRDB's `TaskValueObservationScheduler` — one `Task` draining an `AsyncStream` of notifications — runs the notification; (2) the test's `next()` continuation resumes. GRDB's own side never touches the pool: for the harness's in-memory `DatabaseQueue` the fetch runs on the writer queue inside the commit (`ValueWriteOnlyObserver.databaseDidCommit`) and the reduce on GRDB's `reduceQueue`, both GCD. **Swift Testing 6.4 runs the whole target as child tasks at once**: `defaultParallelizationWidth` is `.max` unless `SWT_EXPERIMENTAL_MAXIMUM_PARALLELIZATION_WIDTH` says otherwise (`Sources/Testing/Support/Serializer.swift`, swift-6.4.0-RELEASE — its `cpuCount × 2` default is commented out), no `Serializer` is installed at `.max`, and `Runner._forEach` adds a child task per suite, test and case eagerly (the one Sonnet lookup; the scratch run below confirms it on this toolchain). Every resumed job joins the BACK of that FIFO queue, so each hop waits for every job enqueued before it — up to the rest of the run. A wall-clock bound on such a wait measures the runner's queue.

**Why `.timeLimit` reds and why only sometimes:** the trait races the body against a sleeping child (`withTimeLimit`, `TimeLimitTrait.swift`: "If sleep() returns instead of throwing a CancellationError, that means the timeout was reached before this task could be cancelled"); the sleep's wake is itself a job queued at its deadline, so the limit fires exactly when a body's resumption is enqueued AFTER the wake — i.e. when one hop of the body waits longer than the limit. The pin's body is enqueued one level deeper than an ordinary test's (the time-limit group's child), so it usually starts near the backlog's end, when little is queued behind it — green most runs, 205 s when it starts early.

### PHASE 2 — the fix: ONE shared harness seam (the held-observation lane)

**The home: the test harness, once, for the class** — not the product (nothing product-side starves; P1), and not a per-test patch (the mechanism is shared by every bounded wait on a held observation in the target; the sweep found a second member that redded naturally in loaded run 2). `Tests/VariorumCoreTests/Support/ObservationLane.swift`:
- **`onTheObservationLane { }`** runs its body in a `Task(priority: .high)` (`observationLanePriority`) — above the `.medium` (21) every Swift Testing test task runs at. A `Task` inherits its creator's priority, so everything made on the lane rides it: GRDB's `.task` scheduler Task (created where the observation is made — hop 1), `HeldValues`' consumer (hop 2), a poll's sleep. The cooperative pool dequeues by priority (scratch: a `.high` resume 0.000 s inside a flood a `.medium` resume waited 4.989 s), so the hops never queue behind the default-priority backlog, and a bound measured on the lane measures the delivery (loaded run 2: max 0.168 s across 80 samples while a `.medium` job waited 57.7 s).
- **`HeldValues`** holds one observation on a consumer task of its own and answers `value(n, within:)` (the `n`th delivery — the `next()` shape) and `latest(where:within:)` (the latest delivery once it satisfies — for an observation that may coalesce), under the harness's one 30 s bound (U1's `HarnessDeadline` precedent). Its init and its waits `precondition` the lane's priority, so a hold made off the lane fails loudly instead of quietly re-opening the class.
- **The rule written at the seam:** make, hold and wait on the lane; bound the wait with `HeldValues`' own bound, never a `.timeLimit` (the test task's own resumption after the lane is outside it, and the trait's limit is measured across that hop: P1's `.timeLimit` analysis).

### THE RIDER — VX-932 (F-U1-1's race), traced and fixed

**The mechanism (read in the code, then forced):** `MCPServerHost.listenerDied` (`Sources/VariorumMCP/MCPServerHost.swift:555–577`) flips `_state` to `.stoppedByItself` UNDER the host lock, releases it, and only then unlinks the socket, closes the listener and calls `onStateChanged` — on the accept thread. A test that waits for `state != .running` and then reads the signal or the socket at once races that thread; load deschedules it between the two. The app is not exposed: its door learns of the death BY the signal, which comes after the removal (program order on the accept thread).

**The fix (test-side, `414f77809`):** three tests in `MCPAcceptLoopServerTests` read post-death facts at the flip, and each now waits: `aFatalAcceptFailureStopsTheListenerAndSaysSo` (the ticket's — `eventually { heard ≥ 1 }`, `eventually { !socketExists }`, then `heard == 1` asserted again before the stop so "once" keeps its meaning); its twin `aFatalPollFailureDoesTheSame` (the same `listenerDied`, the same immediate `heard == 1 && !socketExists`); and `aDeadHostsLaterStopLeavesTheFreshHostsSocket` (it bound a FRESH host right after the flip — before the dead host's unlink, which would remove the fresh socket or make the fresh start meet a live backlog — now it waits for the death to be said first). The waits are the harness's own count-bounded `eventually` (200 × 10 ms), on a fact the accept thread writes — no pool dependency.

**The pin — the descheduled thread made deterministic:** `aSignalLandingLateAfterTheFlipIsStillHeardOnce` runs the same road (`fatalAcceptRoad`, shared with the original test) with the door's signal held 300 ms on the accept thread before it is counted (`signals(_:landingAfter:)`). **R-932** (the two waits back to the immediate reads): RED **3 of 3**, exactly this pin ("heard.value == 1" at the read and again at the "once" check, `revert-R932-{1..3}.log`); restored, the suite **8 / 1 GREEN × 4** (`acceptloop-{1..3}.log`, `acceptloop-after-R932.log`, the gate GREEN). The socket half is not forced by the late signal (the unlink precedes the signal): its wait is the belt, and its ordering is the code's (`:574` before `:576`) — a deterministic arm for it would need a product hook between the flip and the unlink, and `git diff -- Sources` stays empty.

**The runner's width, measured once (informational for P-926-U3-1; `scratchpad/u3/width24/`, idle, the fixed tree + the instrument):** `SWT_EXPERIMENTAL_MAXIMUM_PARALLELIZATION_WIDTH=24` (twice the cores — swift-testing's own commented-out default): 4,015 / 549 GREEN; the backlog GONE — H's first emission **0.232 s** (vs 272.6 s at the default), S max **1.66 s** (vs 188.7 s).
