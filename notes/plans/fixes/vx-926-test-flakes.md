### PHASE 2 — the fix (one mechanism, the three places it reached the harness)

**The mechanism, as the trace settled it:** the harness rides the test process's cooperative pool. Phase 1 found the dominant face (the circular wait: harness waits holding the pool threads the server under test needs — 3–22 s windows with no task run). Building the fix found two more faces of the SAME coupling, each by its own deterministic pin before the fix — so the fix takes the harness off the pool at all three:

1. **The waits — off the pool** (`Tests/VariorumMCPTests/MCPHarnessWait.swift`, `HarnessWait.offPool` / `offPoolThrowing`): every wait whose answer depends on the server under test runs its blocking call on a thread of its own and the test task awaits it (the door's own idiom, `MCPHandshake.openingOutcome`). Sites: `ServerHarness.rawOpen` (now `async`, its 11 files' call sites `await`); `RawSocket.next` / `nextResponse` / `isHungUp` (async); the raw clients `namedClient` / `reachesEOF` / `everyByteUntilEOF` (three files' private copies → one copy in `MCPHarnessWait.swift`; `bareClient` stays local); `MCPCloseReasonTests.pumped`, `MCPShimTests.thePumpCarriesARealSessionVerbatim` and `MCPShimAppClosedLineTests.aRealServerStopUnderALiveSessionIsSaidOnStderr` (the answer read through a real host, and the pump semaphores — the compiler refuses `DispatchSemaphore.wait` in an async body); `MCPPreInitializeWindowTests.aBareOpeningIsAnsweredBeforeTheReadBlocks` (its `async let` handshake needs a pool thread to start); `MCPReaderAfterCloseTests`' initialize wait; `MCPSetupKeyServerTests.expectClosed` and its two window reads (which had NO receive bound at all); `MCPNullIdentifierServerTests.drain`; `MCPLockPostureServerTests.linesUntilEOF`; `MCPConnectionEndServerTests`' inline read; and two sleep-polls on a pool thread made suspending (`Thread.sleep` → `Task.sleep`: `MCPConnectionEndServerTests`' end-line poll, `MCPCloseReasonTests`' handshake pause). The stop-window probe in `MCPStopRoadsServerTests` (a synchronous callback the host runs INSIDE `stop()`) keeps the blocking form and the whole `stop` is made off the pool.
2. **The deadline's clock — its own queue** (`MCPHarnessDeadline.swift`): the timer moved off `DispatchQueue.global()` — a CONSTRAINED root queue that shares its width with the cooperative pool (P-B's first run: a 0.1 s limit fired at 0.81 s with the pool held) — onto `DispatchQueue(label:)`, which targets the overcommit root queue; the expiry carries `HarnessFailure.firedAfter`, read on that timer thread. `MCPHarnessTimeLimitTests`' three belts read it (the two `< 15 s` belts on `firedAfter`; the hang-up test by WHAT answered — no deadline expiry — instead of `< 10 s` of wall).
3. **The bounds — the harness's one** (`HarnessWait.receiveSeconds` = `HarnessDeadline.seconds`, 30 s unless a test shortens it): O-7's rule (the VX-771 run, "at the coordinator's word": four raw helpers given the harness's bound "took them out of the family") carried to every raw wait still on a hand-picked bound — StopRoads' `namedClient` 5 s (left "as it is" by O-7), `RawSocket`'s 5 s default, ReaderAfterClose's 5 s, the bare opening's 3 s, `expectClosed`'s 2 s, ConnectionEnd's inline 5 s. **Untouched, stated so the edge is seen:** every bound's VALUE where it was already the harness's (`rawOpen`, the O-7 helpers, every SDK act's 30 s); the explicit 30 s bounds of the 16 MiB transfers; the 300 ms expect-nothing reads on socket pairs (`MCPPreInitializeWindowTests` — no server involved); the thread-only shim suites with fake apps; ReaderAfterClose's fresh-socket reads (byte already written) and its drain-thread semaphore. `git diff -- Sources` is EMPTY: no product line, no wire byte.

**The three suggestions, one sentence each:**
- **(a) event-driven waits — TAKEN** as (1): the waits suspend until the socket answers on its own thread, which is what removes the circular wait (P-A); the wall-clock receive bound stays only as the never-answers backstop.
- **(b) bounds measured on the harness's own clock/seam (VX-353's) — TAKEN for the one belt that times the harness itself** as (2): the deadline's expiry is read on its own timer thread, on a queue the pool cannot starve; no other test measures the harness's time.
- **(c) a serialized/isolated trait (VX-686's) — NOT TAKEN:** `.serialized` orders tests only within a suite, while the starvation came from ~126 suites sharing the MCP target's one process's pool (each test target is its own process — `VariorumMCPTests.xctest`; a whole-package run adds the core target's CPU load from beside it, never its pool); serializing the family would still leave every other suite's CPU work in the queue and would slow the target, without removing the circular wait.
- **(d) load-scaled bounds — NOT TAKEN as scaling:** a larger bound only lengthens a circular wait (rawOpen's 30 s bound still read 0 bytes in the B4 window); (3) is not a scale but the harness's existing one bound, applied where hand-picked 5 s bounds had been left.

### Self-assessment (how I'd attack this diff — for the cold reviewer)

- **(i) The classification is by reading.** Every blocking call in the MCP test target was inventoried (`grep` over `readFirstLine`, `read(`, `.wait(`, `usleep`, `Thread.sleep`, `accept(`) and each site sorted: a wait whose answer depends on the server under test → off the pool on the harness's bound; a read on a socket pair or pipe the test fed itself, a thread-only fake peer, or bytes already written → left inline. A future test that reads a server's socket inline would re-open the class; nothing structural forbids it (the compiler does forbid the semaphore form in an async body).
- **(ii) One thread per wait.** `offPool` spawns a `Thread` per wait (P-A: 16 at once). Cheap at the target's scale; a long-lived wait parks only its own thread.
- **(iii) Unbounded waits stay unbounded.** The shim pumps' pipe reads (`MCPShimTests`, `MCPShimAppClosedLineTests`, `MCPCloseReasonTests.pumped`) never had a receive bound; off the pool, a server that never answered would now park the test task instead of a pool thread — the same hang it always was, now without starving anyone else.
- **(iv) Failing cases are slower.** A raw wait that times out now waits the harness's 30 s (not 5 s) before it fails — only when the server truly never answers; every SDK act already did.
- **(v) P-B stalls its own run on purpose** — every pool thread held 0.8 s, once per MCP-target run; every raw bound is now ≥ the harness's 30 s, and its premise is informational (asserted only through the deadline's own reading).
- **(vi) `firedAfter` counts from `run`'s arming**, not from the test's own start (a connect's `onDrained` actor hop precedes it): the belt bounds the ACT, which is what VX-132's deadline bounds.
- **(vii) The timer queue is serial** — every deadline's expiry block runs on it in turn; each is O(1) (resume, a `Task` spawn, a cancel).
- **(viii) Task-locals are read before every hop** (`HarnessWait.receiveSeconds` in the task; `RawSocket`'s default argument at its call site; the stop-window probe's bound captured in the test body) — a plain thread sees no task-local.
- **(ix) `git diff -- Sources` is empty;** every pin's subject and every other pin's bytes are unchanged — the converted call sites only gained `await` (and three sync tests became `async`).
