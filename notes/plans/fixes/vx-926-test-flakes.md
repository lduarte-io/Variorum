### The upstream facts (one read-only Sonnet lookup, external sources only; quoted, with the source named — not re-verified line by line here)

- **The modes** (ST-0021 "Targeted Interoperability between Swift Testing and XCTest", Implemented in Swift 6.4 — `swiftlang/swift-evolution` `proposals/testing/0021-…md`; Apple's "Migrating from XCTest" table): `none` — "Interoperability is off. Swift Testing and XCTest ignore cross-library issues."; `limited` — XCTest issues become warnings plus modernization hints (Phase 1's headless table shows exactly this: "Test «unknown» recorded a warning … Replace XCTest API such as 'XCTAssert'…"); `complete` — cross-library issues keep their severity; `strict` — XCTest issues `fatalError()`. Xcode: "Test plans created before Xcode 27 inherit limited mode … For new projects, Xcode uses the complete mode" (WWDC26 #267). The proposal is SILENT on an issue recorded with no test running in either library — the gap this loop lives in.
- **Where the loop is, in the open-source Swift Testing** (`Sources/Testing/Events/Event.swift`, main `99cd1683` and the swift-6.4.0 / 6.4.2 release tags): `Event._post` hands an event to the fallback handler only when there is no current configuration AND `Configuration.all` is empty — no Swift Testing run active — which is Phase 1's timing finding, now from the source. `Event+FallbackEventHandler.swift`'s `_postToFallbackEventHandler` has two guards only: `Interop.Mode.current != .none` (swift-testing PR #1743, merged 2026-06-05, in 6.4.0) and "the fallback event handler belongs to Swift Testing" (an address check). **No re-entrancy guard** — XCTest's handler has another address, is called, and re-enters `Issue.record`. (Release 6.3's `postToFallbackHandler` had neither guard.)
- **The XCTest side:** the open-source swift-corelibs-xctest DROPS an issue when no test case is current and the fallback handler is XCTest's own ("This prevents us from getting into a recursive 'error handling loop'"); Xcode's closed XCTest instead forwards it into Swift Testing (`SwiftTestingInteropRecordHandler.handleIssueRecorded` → `Issue.record`, in every one of our 24 stacks). That asymmetry is the bug report.
- **The entry, on Point-Free's side:** swift-issue-reporting's `TestContext.current` answers `.xcTest` whenever `isTesting` is true and no Swift Testing test is current, without checking for a running XCTest case, so `_DefaultReporter` calls `_XCTFail` — frames 105–107 of every stack. swift-dependencies' documented answer ("Testing gotchas ▸ Testing host application": skip the app's entry when `isTesting`) is what VX-604 built.
- **Prior reports:** none found — no swift-testing / swift-corelibs-xctest / swift-issue-reporting issue or PR, no Swift-forums thread on this recursion (Apple's own forums and Feedback could not be read). Nearest relatives: swift-testing #1542/#1543, #1743; corelibs-xctest #538, #542.
- **The test-plan key** (undocumented in prose; seen in real files): `.xctestplan` `defaultOptions.testInteropMode` (a string, e.g. `"complete"`); `.xctestrun` `TestInteropMode`.

### The Apple Feedback draft (a deliverable — hers to file by hand in Feedback Assistant; no ticket ids, plain words)

> **Title:** Swift Testing / XCTest interop: an issue recorded while no test is running recurses forever between XCTest's interop handler and Swift Testing's fallback event handler, crashing the test host with a stack overflow
>
> **Area:** Developer Tools › Xcode › Testing (XCTest and Swift Testing)
>
> **Environment:** Xcode 27.1 (27A9275) · macOS 27.0.1 (26A434) · Apple Swift 6.4 (swiftlang-6.4.0.34.1) · Swift Testing library version 2084 · Apple silicon. A macOS app with an app-hosted unit test bundle (Host Application = the app); the tests use Swift Testing only (no XCTest tests, no XCTest assertions); run with `xcodebuild test` / `test-without-building`, default interop mode.
>
> **Summary:** When code in the test host app records a test issue at a moment when no XCTest test case and no Swift Testing run is active — for example a few seconds after launch, after a short Swift Testing run has already finished, or before it has started — the host crashes with EXC_BAD_ACCESS (SIGSEGV), KERN_PROTECTION_FAILURE at the main thread's stack guard ("Could not determine thread index for stack guard region"). The crash report's recursion information shows a 13-frame cycle repeated 931 times (original stack length about 12,165 frames). XCTest's fallback issue handler passes the issue to Swift Testing; Swift Testing, with no run active, posts it to the fallback event handler XCTest installed; XCTest's interop record handler records it again as a Swift Testing issue; and nothing stops the cycle.
>
> **The cycle, from the crash reports (callee first):** Testing `JSON.withEncoding` → `ABI.Version.eventHandler(encodeAsJSONLines:forwardingTo:)` closure → `ABI.Version.eventHandler(forwardingTo:)` closure → `Event._post(in:configuration:)` → `Event.post(_:for:instant:configuration:)` → `Issue.record(configuration:)` → `static Issue.record(comments:severity:sourceContext:)` → libXCTestSwiftSupport `SwiftTestingInteropRecordHandler.handleIssueRecorded(_:)` → `handleRecord(_:)` → XCTestCore `Interop.Handler.defaultHandler` closure → Testing `closure in static Event._postToFallbackEventHandler` → `JSON.withEncoding` → … (repeats).
>
> **The entry (the bottom of every report):** the app reads a swift-dependencies dependency during launch, outside any test; swift-issue-reporting's `_DefaultReporter.reportIssue` calls `XCTFail` (its context is "XCTest" because no Swift Testing test is current) → `_XCTPreformattedFailureHandlerWithIssueBlock` → `XCTFallbackIssueHandler.handle(_:)` → `XCTFallbackIssueHandlerSwiftSupport.passToFallbackHandler(issue:)` → the cycle.
>
> **Why it looks like a JSON encoder crash:** each turn of the cycle JSON-encodes the event record, so the guard page is usually met inside the encoder. In 21 of our 24 reports the top frame is `swift::MetadataCacheKey::operator==` or `StableAddressConcurrentReadableHashMap::getOrInsert` under `Dictionary.reserveCapacity` under `__JSONEncoder.container(keyedBy:)` in `ABI.EncodedEvent.encode(to:)`; in 3 of 24 it is `___chkstk_darwin` under `__JSONEncoder.wrapGeneric` under `ABI.Record.encode(to:)`.
>
> **Steps to reproduce:**
> 1. Create a macOS app target and a unit test bundle hosted by it. Give the bundle one Swift Testing test: `@Test func passes() { #expect(Bool(true)) }`.
> 2. Add the swift-issue-reporting package to the app. A few seconds after launch, report an issue from outside any test — for example in the `App`'s `init`: `Task { try? await Task.sleep(for: .seconds(3)); reportIssue("reported outside any test") }`.
> 3. Run only that test: `xcodebuild test -scheme <App> -destination 'platform=macOS' -only-testing:<AppTests>`. The Swift Testing run finishes before the delayed report lands.
>
> **Expected:** the issue is reported once (attached to the run as an issue without a test, or dropped with a diagnostic), and the host exits normally.
>
> **Actual:** the host crashes with a stack overflow (931 recursions); xcodebuild prints "Restarting after unexpected exit" and Problem Reporter opens. In our project a one-suite run crashed on 3 of its 4 tests. Whether a run crashes depends on when the report lands relative to the Swift Testing run, so short selections crash most often; in long runs the same report attaches to the run instead. (Our project's own crash comes from exactly these steps' shape; we have not built this minimal project, because the crash requires the Xcode test runner.)
>
> **Notes:**
> - Under `swift test`, where XCTest and Swift Testing run as two separate processes, the cycle never forms: in 31 runs covering every out-of-test road we could build, such issues were silently dropped instead.
> - In the open-source Swift Testing (swift-6.4.0-RELEASE and main), `Event._post` uses the fallback event handler only when no configuration is active, and `_postToFallbackEventHandler` guards only against calling Swift Testing's own handler, so XCTest's handler is called and re-enters `Issue.record`. The open-source swift-corelibs-xctest drops an issue when the fallback handler is XCTest's own ("This prevents us from getting into a recursive 'error handling loop'"); the XCTest in Xcode 27.1 forwards it into Swift Testing instead. A re-entrancy guard on either side would end the cycle.
> - `SWIFT_TESTING_XCTEST_INTEROP_MODE=none` should stop Swift Testing from posting to the fallback handler, but it also discards cross-library issues; we have not verified it. Our workaround was to keep the host app from doing any work under a test runner.
