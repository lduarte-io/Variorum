## 4. The binding principles (the 13b constitution, P-1…P-9 — copied per the architect-phase skill; byte-verbatim)

- **P-1 — One capability registry.** Every user-facing act is declared exactly once: verb, scope (block/take/post/book), per-mode availability rule, its doors (menu / context / bar / shortcut / palette), and its refusal copy. Surfaces render their doors FROM the registry; gating is data, never per-view if-statements. A registry-walk test asserts every declared door exists and every rendered door is declared. This kills the D3/D4 class structurally — the capability matrix stays green by construction instead of by audit.
- **P-2 — Fire-and-DO (R115).** A rendered door either performs the act — including any mode-switch choreography, done visibly for the user — or delivers the operations layer's real refusal. A door that can never act in its context isn't rendered. Lecture-and-redirect is retired.
- **P-3 — One text surface, one liveness authority.** ONE TK2 surface component (live + read modes; one measurement brain — the width-gated remeasure; the shared canary) that every pane composes; the live editor core's identity machinery (`BlockRangeIndex`, crystallization) becomes its live mode, not a sibling implementation. "What text does this pane show, and is it live" is answered by ONE pure, unit-tested authority (`PaneTextAuthority`); views never re-derive it. Its invariants stated as code: exactly one live pane; the live pane is buffer-authoritative; read panes are projection-authoritative once caught up.
- **P-4 — Broadcasts carry signals, never decisions.** NotificationCenter may announce that something happened (mode changed, post opened); no listener derives business state or availability from a broadcast, and no flow's correctness depends on broadcast ordering. Cross-feature flows route through composition. (Stage 0's survey enumerates today's notification bus; Stage 1 disciplines it.)
- **P-5 — The friction doctrine (R116).** Repeated pushback against a rule marks an under-architected feature. The response is never another patch: write the feature's DESIGN MEMO — intended behavior whole, edge cases enumerated on paper, refusal wordings, undo story — get the author's rulings on the product-flavored edges, then build to the memo. Happy path ships first, but the edges are *decided at design time*, not discovered by the author. First two memos owed: **merge** and **the W ceremony**.
- **P-6 — The tutorial is the executable spec (R113).** The guided tutorial flow is the contract for every happy path. It stays green — automated where the harness allows, screenshot-walked otherwise — and any change that breaks a tutorial step is a regression by definition.
- **P-7 — Find bugs before she does.** Every layer keeps a proactive harness: the ops-layer soaks (exist), the board/view-model invariant soak (Stage 1), the registry walk (P-1), the per-batch scripted screenshot walkthrough. Red-on-old stays absolute: no bug-class fix without a pin that fails on the pre-fix code.
- **P-8 — Standing law, consolidated.** P1–P3 performance invariants bind the rebuilt layer exactly as they bind the substrate (invalidation ∝ realized rows; one live editor; virtualized long views). Overlays, never rendering attributes. Chrome `fixedSize` texts always carry a `lineLimit` (the b6dae25 class). `Theme/VoiceControls.swift` is THE chrome vocabulary. Complexity lives in the store; restraint lives in the UI.
- **P-9 — No god objects in the frontend either.** A view model mixing board layout, text authority, and gesture routing splits by concern (`TakesViewModel` at 890 lines is the standing counterexample). Same hygiene rule as the substrate, applied where it was being waived.

##### Unit B — THE SYNC-HALF DESIGN PROPOSAL (the 4E pattern; for the orchestrator's ruling against §6 and SyncSpec)

**0. What today's engine does with the two new acts (traced, so the rails have a mechanism to answer).**
- *A user delete looks exactly like a keeper retirement on the wire.* Both are `reading.deleted_at` set on a row still wearing `profile='daily'` (`deleteReadingRow` today refuses, so the shape has never been produced by her hand on this build; `convergeDailyJournalDuplicates` writes it at `Repairs.swift:1063`). Every keeper leg keys on that shape: direction 1 (`Repairs.swift:218–232`, `journalKeeperBesideRetiring` `:258–276` — the LOCAL row's shape OR the ARRIVING columns') hands the dead book's live children to `dailyJournalBookCandidates.first { $0 != row.rowID }` — any other live candidate, of either id order; direction 2 (`:285–303`) re-points a live child arriving under a dead mint-shaped parent; the fresh-store leg is direction 1 with no local row.
- *So delete-then-remint backfills by three doors.* (i) A device holding the old Journal live (with its own unpushed offline filings) applies the new Journal and then the old one's tombstone in one batch (the same push drains `reading` rows by ascending id — `precedesInDrain` `SyncEngine.swift:420` — so a re-mint with the smaller id reaches the server FIRST): direction 1 moves the old book's children into the re-mint. (ii) A late live child of the old book (an offline filing pushed inside the A5 band, or by the API-legal push-without-pull) arriving where the old book is dead and the re-mint live: direction 2 re-points it into the re-mint. (iii) A pull landing between two chunks of that same push sees TWO live `'daily'` rows: the post-batch keeper MERGES them — and when the old id is the smaller, it RETIRES THE RE-MINT (her new Journal goes to the Trash on every device) and then the old book's own tombstone arrives: no Journal at all.
- *What CAS already saves.* Every membership the DELETER saw dies by its own cascade, pushed at a newer version than any third device's re-point; the tombstone-wins overlay (`Merge.swift:37–39`) keeps it dead in both push orders. The backfill that sticks is the filings the deleter never saw (other devices' offline days) — and door (iii)'s dead Journal.

**1. Rail 3 — the discriminator: THE DELETE CARRIES ITS OWN MARK (recommended, option A).**
- **The rule, in SyncSpec §7's terms:** *a keeper retirement is recognized ONLY by a tombstone wearing the daily marker; her deliberate delete of the daily Journal stamps the tombstone with the DELETED-JOURNAL marker instead* — `reading.profile = 'daily_deleted'` (PROVISIONAL spelling; one constant beside `dailyJournalBookProfile`), written by `deleteReadingRow` and `deleteReadingWithNotes` in the same row write as `deleted_at` whenever the book wears `'daily'`. A `'daily_deleted'` tombstone is an ORDINARY delete everywhere: its cascade takes its children (direction 1 stands down — the arriving columns are the verdict), a live child arriving under it joins its cascade (direction 2 stands down — `isDailyJournalMintShape(parent)` is false), the fresh-store leg stands down, and the post-batch keeper never sees it (live rows only). The retirement's own tombstone is byte-unchanged (`'daily'`), so **the true duplicate-mint race converges exactly as today** — every existing keeper pin keeps its expectation.
- **Why the delete carries the mark, not the retirement:** R-805-2's no-standing clause ("the old book simply returns as THE Journal — the marker rides the row") needs the dead row to REMEMBER it was the Journal; the sentinel is that memory, and restore normalizes it (item 4). A mark on the retirement instead (demoting the loser to the trait) cannot tell a retired loser from any deleted journal-TRAIT book — direction 2 and the fresh-store leg would then backfill a dream journal into the daily Journal.
- **No wall clock anywhere; three belts on the order:**
  - (a) **The drain sends a `'daily_deleted'` tombstone ahead of every other `reading` row of the same push** (`precedesInDrain` gains one key inside `reading`: sentinel tombstones first, then ascending id — R2-7's keeper-insert-before-loser-tombstone order is untouched, because a retirement tombstone wears `'daily'`). So a re-mint never reaches `server_seq` before the delete it follows — same-device same-push included — and a chunk split keeps that order (chunks commit in seq order per tenant since 13y). Cross-device, causality already guarantees it (the re-minting device pulled the tombstone first). This belt also protects OLDER builds (her phone until its next install): their direction 1 reads only "another live candidate stands" — with the delete always first, none does.
  - (b) **The merge carries the mark** (`Merge.swift`, the tombstone-wins overlay, `reading` only): a local tombstone's `profile` rides the overlay over a LIVE server row (today only `deleted_at` rides — her delete, rejected by a concurrent rename of the Journal on another device, would otherwise land wearing `'daily'` and read as a retirement); and where BOTH sides are tombstoned, a local `'daily_deleted'` outranks a server `'daily'` (her deliberate delete outranks a repairer's retirement made on an incomplete picture — the door-(iii) residue below). This is SyncSpec §6's own metadata clause ("re-apply local intent on top if still meaningful") applied to one column of one table; every other column stays server-wins.
  - (c) **Direction 1 reads the arriving tombstone first:** an arriving `'daily_deleted'` returns "ordinary delete" before the local-row leg is consulted (`journalKeeperBesideRetiring`). The local leg otherwise stays exactly as built (minimal change; it still covers an older build's retirement merged with a concurrent profile change).
- **Residual corner (recorded, not closed):** her delete REJECTED by CAS in drain iteration 1 while the same push's re-mint was ACCEPTED (iteration 2 re-sends the merged tombstone) inverts the order; a pull landing in that gap meets door (iii): the third device merges, its own unpushed offline filings of the old book re-point into the re-mint (minor backfill of THAT device's days only — the deleter-seen ones die by CAS), and belt (b)'s `(true, true)` arm restores the sentinel shape when her tombstone lands. Needs: a concurrent edit of the Journal's row elsewhere + delete and re-mint in one drain + a pull in the seconds between iterations. A drain rule closing it ("a rejected sentinel tombstone ends the iteration before any later `reading` row is sent") is available if the ruling wants it; not proposed (machinery for a three-coincidence corner).
- **Mixed fleet (her phone on an older build until its next install):** an older build cannot delete the Journal (its op refuses); it reads `'daily_deleted'` as an unknown profile — its direction 2 and fresh-store legs stand down on it (not mint-shape), its direction 1 local leg can fire only if a re-mint is already live when the tombstone lands, which belt (a) prevents; an older build RESTORING a sentinel book gets a plain book (not THE Journal) — the one degraded face, gone at its next install.
- **Not DDL, but a schema-semantics fact — FLAGGED FOR THE RULING:** a new VALUE in `reading.profile` (unconstrained `TEXT`, no CHECK — `Migrations.swift`; PLAIN under E2EE: an enum, no prose), living only on tombstoned rows (restore normalizes it, purge removes it). No migration, no mirror change, no lockstep marker bump. SyncSpec §12 calls "a change that alters the meaning of an existing synced column" a redesign-level event to be designed in SyncSpec first — this proposal is that design, but whether a new enum value needs HER word is the orchestrator's call (and AppSpec §7's `reading.profile` comment gains the value at closeout either way).
- **Option B (no new value):** the delete DEMOTES to the trait (`'journal'`). Clean on the wire for directions 1/2 only if the local leg is also dropped — and R-805-2's no-standing clause can no longer hold (the dead row forgets it was the Journal, so a restore with no standing Journal brings back a trait book). Needs her re-ruling of R-805-2. Not recommended.
- **Option C (seq only, no mark):** "a dead `'daily'` tombstone is a retirement only if the smallest other live candidate is the smaller id AND its known `server_seq` precedes the tombstone's" (never-accepted = after everything). Fundamentally blind to the same-push re-mint with the smaller id (its rows are byte-identical in shape and seq order to R2-7's retirement), and it regresses the race's late-child leg whenever the keeper's row was touched after the retirement (a rename, a star, an un-archive by ⌘J). **4. Rail 4 — R-805-2 under sync.**
