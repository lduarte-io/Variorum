The approval moves the grants fingerprint, so the host's observation asks this connection to announce; nothing waits for that notice. The test then builds and sends a 16 MiB + 1 line, reads the over-cap answer through `nextResponse()` (which SKIPS a notice that arrives before it), and calls `isHungUp()`, which is `read(fd, &byte, 1) == 0`. A notice that arrives AFTER the answer and before the server's `shutdown` makes that read return 1 → false → exactly the one recorded failure (line 158 alone; the three answer expectations before it green, as recorded). A late notice between the answer and the close breaks no contract (MCPSpec: "answered … then closed"), so this is a TEST defect if confirmed, not a product one.
