1. **2026-07-07 · cross-app · The Fragments journal bridge — one-way, two-way, or skip? [ANSWERED — see note above]** The author's Fragments app (iOS, `~/dev/fragments`) ships a deliberately minimal "journal satellite" *explicitly designed for a co-writer journal app*: Supabase table `journal_entries` keyed `(user_id, date)`, plain-text `body`, deterministic UUIDv5 id `journal|<user>|<dayKey>`, row-LWW, RLS — the table is its only external ingress, by design (Fragments SyncSpec §8). Connecting Variorum costs the model **nothing**: the contract wants one plain-text body per day, which is exactly `renderedText` of a journal post — a one-way read-side projection push; blocks/fans/commits stay Variorum's own. Options: **(a) one-way push** Variorum→Fragments (display in Fragments' Day screen; needs a second transport + auth to Fragments' project, dayKey/UUIDv5 derivation, change detection, and an edit-war rule for days Fragments' own editor also wrote); **(b) two-way** (Fragments edits flow back via ordinary `autosave` — S5 covers conflicts — but that makes Fragments a second capture surface right as Phase 8 gives Variorum its own); **(c) skip** (accept two disjoint journals — the bifurcation is the real cost of skipping). **Decide after Phase 8** with a few weeks of real usage evidence about where she actually journals; the build is small once decided. **Status: open — author call, deliberately postponed for evidence.**

4. **2026-07-07 · Phase 8 · A4 daily-drive mechanism.** The fence shipped: debug builds default to the separate dev store (`Variorum-dev/`); the real store from a debug build needs `-VariorumRealStore` / `VARIORUM_REAL_STORE=1`; release opens the real store. **The sync seam is fenced too (review round 1, BLOCKER — so her ratification is informed):** debug and release builds share a Keychain, and there is exactly ONE production mirror — so an ungated dev-store session would have auto-adopted her pasted credentials, pulled her corpus into the dev store, and pushed dev-session writes to the mirror (which replicates to her real devices). Now a dev-store session **never syncs at all** (no credential auto-load, no setup door — the status row says "Sync off (dev store)"); the one mirror pairs with the real store only. Consequence to ratify with the mechanism: a blessed-debug daily-drive via the opt-in gets real store + sync, exactly like Release; plain debug/dev work is fully offline. **The iOS consequence (review round 2 — read before the device round):** the opt-in exists only when Xcode launches the process; a DEBUG build installed on the phone and launched from the home screen always resolves the dev store, where sync is fenced OFF (no setup door) — so the phone must be installed as a **Release** build for the checkpoint's credential paste and device rounds (Xcode: Product → Scheme → Edit Scheme → Run → Build Configuration → Release, then run to device once). Alternating an Xcode debug launch (args present) with home-screen launches would also silently split the phone's journal across two stores. If Release-install feels wrong for the phone, the alternative on the table is **iOS defaults to the real store** (the simulator's container never touches her corpus; the fence's iOS value only guards hypothetical future on-device dev builds) — her call. **Her call (plan A4): daily-drive a Release build, or a blessed debug run via the opt-in — and the iOS install mode above.** **Status: open — author call at the checkpoint.**

5. **2026-07-07 · Phase 8 · `newBlock` never stamps `last_touched_at`/churn — spec alignment?** Found while building the idle sweep: `newBlock` (and the mint helpers under it) writes no touch stamp and feeds no churn, so a mint-only post (one-burst entry; a teardown-minted tail; drag-drop bulk) never moves in the touched sort and — without the sweep's added `created_at` branch — would be invisible to idle insurance forever. AppSpec §10 says *text-changing ops* update `last_touched_at` and churn, and the 2026-07-06 delta stamps even structural ops ("restructuring is working on the post") — typing brand-new text arguably must stamp *a fortiori*. Options: (a) `newBlock` calls `registerTextChange` (stamp + churn = the minted text's length) — spec-truest, but changes Phase 2-tested op behavior and every mint call site's expectations; (b) stamp only, no churn; (c) leave as-is — **with the honest coverage statement (corrected per review round 1, which caught the original overclaim):** the sweep's `created_at` branch covers *never-touched* posts only (a fresh one-burst entry). A mint into a **previously-touched post whose stamp is already behind the sweep mark** — an idle-/teardown-minted tail on an old post, left alone afterwards — is invisible to BOTH branches and gets **no idle insurance until the post's next real edit**. *Same family (round 2): a never-touched post CREATED before the mark and filled later — e.g. a "Today" page opened blockless one day, swept past, then given its one block days later — is equally invisible (the created_at branch windows on creation, not the mint).* Those residual gaps are pinned/documented (`aMintIntoAPreviouslyTouchedAndSweptPostIsMissed_documentedGap`) and are exactly what (a)/(b) would close. The sort gap is cosmetic and rare since real typing autosaves immediately after. **PROVISIONAL: (c) for this phase** — no op-behavior change mid-phase. Suggested owner if (a)/(b): Phase 9, where crystallization mints live in the editor. **Status: open — author call (now on the corrected premise).**
