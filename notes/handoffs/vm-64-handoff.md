   **The keystroke fence (VM-2) — the two that change what you see:**
   - **P-2-1 — a key typed while a structural act lands is refused, and the phone says so.** *Now:* while a Divide, Merge, Extract, Make Block, a block delete or archive, or the undo door's Undo or Redo is landing (from the moment the act saves your typing until the page shows its result), a key, an autocorrection, a paste or a formatting button is not written. Once the act has landed, the message line at the bottom says "Another structural change is still landing." That line has no Undo button; the act's Undo stays in the note's ⋯ menu. Words you are dictating while it lands are held back and the page is re-read from your library. A key refused or held back this way never writes old text, and nothing is dropped without that sentence. (Two rarer roads by which old text can still be written — a timer's save, and a key typed in the moment after the fence has lifted too early — are listed under "What was found and not fixed" below.) *The alternative:* hold the keys and type them again once the act lands — the first design, and the Mac's way. *Why it changed:* your keyboard asks the editor before every key it types (your own phone's trace from 2026-08-23 shows the ask before every key and every autocorrection), and once the editor says no, the keyboard never types the key, so a hold could only ever catch keys typed by tests. ## What shipped

**The timing readout (VM-65).** The phone now measures, in every build, the moments you named: the tap on the capture box, the keyboard coming up, File, Open, the note on screen, unlock, the library ready — plus counts the later fixes answer to (note reads per open, Library re-reads per save, savepoints per leaving, the owner check, sync rounds). It records durations and counts only, never text, titles or ids; it costs almost nothing per moment and its memory is capped. It keeps its numbers in the app's own folder, outside your library, one table per build. The Mac compiles the same marks and records nothing. No before → after here: this is the instrument.

**The keystroke fence (VM-2).** A key typed while a divide, merge, extract, make-block or structural undo landed used to write the block's old text back over the act's result: a divided half read twice, an extracted span twice, and a merge could carry your words into a block that had left the note. Now such a key is refused and said (P-2-1). Eight tests failed on the old code and pass now, alone and beside 48 other editor suites.

**The speed tests run your paths (VM-66).** One new test suite drives the real note screen and the real shell, and reads the timing layer's own numbers; a test library spread over nine wings joined the fixtures. It produced the run's BEFORE numbers, which every later fix was judged against.

**Launch and unlock stop scanning every table (VM-67).** Every launch, unlock and sign-in read every row of eleven tables inside a write to find rows without an owner, and nearly always found none. Now an index holds exactly those rows, so the check asks the index and writes nothing when there is nothing to adopt. Simulator, 450 notes: 1.16 ms → 0.77 ms. On the Mac, headless, at 61,700 rows: 11.1 ms → 0.8 ms; the old cost grew with your library and the new one does not.

**The Library pages and stops re-reading (VM-68).** The Library, even off screen, re-read and redrew its whole listing at every save, and it silently stopped at 200 notes. Now it loads pages (every note reachable), holds nothing while you cannot see it, and re-reads once when you return. Hidden-Library re-reads per capture-box save 2 → 0 and redraws 2 → 0; one re-read per return. **One page fetch is not faster:** on the 450-note test library a page took 1.90 ms against the old listing's 1.16 ms (Bookless 8.21 ms against 6.86 ms). What changed is how often it runs (never while hidden) and how it grows: the Bookless page's work stayed flat from 300 to 1,200 notes, where the old read's grew fourfold.

**A note is read once (VM-69).** Opening a note read the whole note twice, laid out its margin marks three times, and its book and tag chips read every book and every tag you have. Now one read, one layout, and the chips read only the note's own rows. Note reads per open 2 → 1 on every road measured; the 100,000-word note is live in 342 ms instead of 496 ms. The short-note timings did not move beyond noise. The suspicion that the editor was built twice per open was checked: it is built once.

**A note's editor is released when it closes (VM-70).** Nothing on the phone gave back an editor's save queue, so the list of them grew by one per note opened. Now leaving gives it back as its last act, after your typing and the savepoint have landed. Growth per open and close: 1 → 0. The first version put the release where your app never promptly reaches it; a test window caught that and it was rebuilt.

**Leaving saves once (VM-71).** Leaving a note made the one runner re-read the whole note to find what needed a savepoint (on the Mac, headless, about 216 ms for the 100,000-word note, edited or not), and backgrounding under Castle did it three times. Now a quick read off the runner finds what is owed, and the runner writes only that. Castle backgrounding 3 → 1 savepoint attempts, the lock 2 → 1. Simulator, the 100,000-word note: after only reading it, the runner was held about 159 ms with all 1,404 takes read, and is now held about half a millisecond with none read; after one edit, about 159 ms → about 7 ms, one take read. On the Mac, headless: 216 ms → 1.07 ms. The capture box's first save right after that leaving: about 152 ms → about 8 ms on the simulator (the before figure is from the same test run on the build without this fix). What leaving does to the lock did not move.

## What was found and not fixed

Each has an owner; the full table, with where each item is recorded, is in `notes/plans/fixes/vm-64-closeout-drafts.md` ▸ (g).

- **During a divide or merge, two rare roads can still write a block's old text** (**VM-226**). First, the idle save of the words at the end of the note, when the act divides or merges the note's last block: a timer's write, not a key. Second, when that idle save lands inside a divide or merge, the fence can lift a moment before the page has re-read from your library, and a key typed in that moment can write the old text. Both are rare, and no text is lost: both versions are kept on that block, one of them as an extra take. And one more found in the last review: if a save in a note is stuck and cannot land, pressing Divide or Merge there — even where the press refuses — leaves typing refused in that note until you close it and open it again.
- **A note covered by another screen and shown again while its leaving is still flushing** stops hearing its save queue until a full leave-and-return: narrowed by this run, not closed (**VM-227**).
- **The minute-long sync round with nothing to send** is not this run's to fix. The owner check is not its cause (it runs before the round, in milliseconds). Splitting the minute needs marks inside the sync engine (VM-232).
- **After every clean sync round the phone scans four whole tables for deleted rows** (**VM-182**, wave 4).
- **Each quick note's filing reads the Keychain** to stamp its owner, on your second lag's road, unmeasured (VM-233).
- **A fresh install's first launch recorded no launch times** on the walk; whether by design is untraced (VM-234). Your in-place install is not a fresh install. The same ticket now also holds the two readout cautions from the last review (a Launch row can include time the phone spent starting the app before you touched it; "Note reads per open" can show 2 after an open you backed out of), each with the small fix it would take.
- **A signed-out phone's local purge loop may scan for deleted rows** (VM-235).
- **The fence covers block delete, archive and the cross-block edit by construction, with no test of its own** (VM-236).
- **A save queue left unsaved at its last release is never dropped** once its write lands: a small, bounded growth (VM-237).
- **After Open, the caret sits at the start of the typed line** (**VM-77**, wave 2). **After a Castle relock, the capture box keeps using the closed library** (**VM-107**, wave 2). **The sync round still runs inside the background window before the lock** (**VM-103**, wave 2).
- **The shown Library still re-reads its first page at each save**; narrowing that is **VX-618**, which stays open. And under the three sorts other than "edited", or in a wing holding fewer than 200 notes, that one read grows with the number of notes in your whole library (**VM-240**, for wave 4's speed pass).
- **A change arriving by sync to a note far down the Library list** (past the first 200 loaded) is not shown until the list next refreshes, as it does when you leave the Library and come back (**VM-242**). The same thing done on the phone itself (a delete, a star, an Undo of a delete) is shown at once: the round-2 review found that gap and it is fixed.
- **The speed tests run only when asked** (they read the app's one timing record, so they must run alone), so a few of the counts this run fixed are checked only when someone runs them: the Library doing no reading and no redrawing while it is off screen or covered by a note, through the real app screens, and the editor built once per open. Tests that run every time, for those counts, are **VM-241**. (A note read once per open already has one, added in round 2.)

**Old tickets this run touches, at your word:** VX-618 stays open (above). VX-68, the gate-less-insertion and flicker watch, stays open: the readout times moments and does not watch for a flicker, and this run changed nothing on that road. VM-1's autosave-registry part is delivered by VM-70. VM-13's performance part is the readout run at your sitting.
